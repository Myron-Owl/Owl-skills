# 第 1 章：什么是着色器

### 第 1 章：什么是着色器 —— 从 CPU 到 GPU
**学习目标**：理解 shader 的本质——它不是"画图的程序"，而是 GPU 上并行运行的微型程序；理解 CPU 和 GPU 的根本分工差异；能用自己的话说出渲染管线中 vertex shader 和 fragment shader 各自负责什么。

**场景搭建**：本章为纯概念章，不需要在 Godot 中搭建场景或编写 shader 代码。

**内容要点**：

- CPU 串行计算 vs GPU 并行计算：为什么单靠 CPU 画不完一帧游戏画面
- 并行的代价：GPU 线程"看不见邻居"也"不记得过去"——这两个约束塑造了 shader 的一切
- 渲染管线极简版：顶点输入 → 顶点着色器 → 图元装配 → 光栅化 → 片元着色器 → 帧缓冲
- vertex shader 和 fragment shader 的分工：一个管位置，一个管颜色
- shader 在游戏中的六类应用（材质 / 顶点动画 / 角色特效 / 屏幕后处理 / 风格化 / 程序化生成）
- Godot 中 shader 的挂载方式与五种 shader_type

---

#### 1.1 一帧游戏画面，到底要算多少次？
想象你在玩一个画面分辨率是 1920×1080 的游戏。整个屏幕上大约有 200 万个像素。如果游戏以每秒 60 帧运行，那么 GPU 每秒需要决定这 200 万个像素各自应该显示什么颜色——一共约 **1.24 亿次**"这个像素该是什么颜色"的判断。

这还没完。如果是 3D 游戏，每个像素的颜色又取决于场景中物体的位置、光照方向、材质属性、透明度叠加等等。把所有这些因素算进去，**每秒需要完成的数学运算量是一台 CPU 根本无法串行扛住的**。

这里的关键词是"串行"。CPU 的设计哲学像一个极端高效的单人厨师：它可以同时煎牛排、切洋葱、搅汤，但本质上它只能一件一件来做——把牛排翻个面，再去切两刀洋葱，再回头搅一下汤。CPU 的"同时做很多事"通过极快地切换任务来实现，更准确的说法是**并发（concurrency）**而非真正的并行。CPU 同样拥有多核心和 SIMD 指令集来做并行计算，但它的设计目标始终是**低延迟、复杂逻辑和灵活的任务调度**——它要同时跑操作系统、后台服务、游戏逻辑、物理计算，每一项任务的性质都不同。

GPU 的设计哲学完全不同。它像一个拥有几千个小灶台的厨房，每个灶台只负责一颗米粒。你同时把几千克大米倒进这几千个灶台里，它们同时开火，一瞬间全部煮熟。

GPU **牺牲了灵活性，换取了海量相似任务的吞吐量**。它擅长的是"几百万个像素，每个都做几乎一样的计算"。它不擅长处理分支、跳转、复杂的数据依赖——这些东西会打乱并行的节奏。

这就是 GPU 的核心能力：**大规模并行计算**。

但是，这个能力是有代价的。

---

#### 1.2 并行的代价："盲线程"与"无记忆"
GPU 上同时运行的几千个线程，每一个在逻辑上都是**完全独立**的。这种独立性带来了两个根本约束，也正是 shader 编程之所以"难"的根源。

**约束一：线程互盲。** 一个线程不知道、也不能问"隔壁线程在算什么"。为什么？因为允许线程之间互相询问，就意味着需要在几千个线程之间建立通信通道。在任何时刻，如果某个线程的运算依赖于另一个线程的结果，那么它就必须等着——而"等待"是并行计算最大的敌人。一旦有等待，就退化成串行了。

在写 shader 时，GPU **为了保证并行效率，不鼓励片元之间直接通信**。在实践中，"看隔壁像素"的需求只能通过多遍渲染（multi-pass）来实现——先把第一遍的结果画到一张纹理上，第二遍再读那张纹理。这是后话，但根源就在这里。

**约束二：线程无记忆。** GPU 线程不知道它"上一帧"在做什么。一个线程忙完一个像素，GPU 会立刻塞给它下一个完全无关的任务——可能是游戏界面上的一个按钮，然后是天空中的一片云，然后是一封邮件里的文字。它没有"我上次画的是一个红色像素"这样的概念。

这意味着 shader 把所有像素的计算逻辑都压缩成了一个**纯函数**：输入几个参数，输出一个颜色。它不能依赖全局状态、不能记录历史、不能跨像素——因为 GPU 根本就不会给它保存这些东西。在传统的顶点/片元着色器（本书第 1–4 部分重点讨论的范畴）中，这个模型基本成立；后面接触到计算着色器（Compute Shader）时，我们会看到少量突破这一限制的方法——计算着色器可以通过共享内存让同一工作组内的线程交换数据，不过那已经是另一种设计范式了。

这两个约束——看不见邻居、不记得过去——可以从一个角度概括：**shader 程序不是"指挥几千个小兵协同作战"，而是"发布一条命令，让几千个小兵各自独立执行"。**

理解了这一点，你就理解了 shader 编程为什么是现在的样子。后面你会看到的所有 shader 技巧——用 fract() 做循环、用噪声代替随机数、用 smoothstep() 代替 if 分支——追根溯源，都是在"盲且无记忆"的前提下，用纯数学来表达视觉效果。

#### 1.3 那么，什么是着色器？
有了前两节的铺垫，"着色器"的定义就不再是一句空洞的术语了：

**着色器（shader）是运行在 GPU 上的一个微型程序，它接收一组输入数据，对每个顶点或每个像素独立地执行同一段计算逻辑，最终输出这个顶点应在屏幕上的位置、或这个像素应显示的颜色。**

把这句话拆开来理解：

- **"运行在 GPU 上"**：shader 不是 CPU 程序，它不吃 GDScript 那套"一行一行走、有变量、有循环、有状态"的模型。
- **"对每个顶点或每个像素独立地执行同一段计算逻辑"**：这就是并行的本质——所有顶点/像素同时跑同一段代码，但输入的顶点位置或像素坐标不同，所以输出不同。
- **"最终输出位置或颜色"**：这是 shader 最原始也最核心的两件事——顶点着色器负责这个顶点该放在屏幕哪个位置，片元着色器负责这个像素该是什么颜色。所有炫酷的效果——水面、火焰、护盾、卡通渲染、老电视——都是这两件事的花式玩法。
与 C++、Python 这类通用编程语言不同，shader 是**单一用途的微型程序**。通用语言可以写操作系统、写网页、写数据库——它们什么都能做。但 shader 只做一件事：接收顶点或片元数据，运行一段固定的计算，输出位置或颜色。它没有文件系统、没有网络、没有多线程——GPU 上的一切资源都只为"并行处理图形数据"这一件事服务。这种极端专注不是限制，而是它如此高效的原因。

一个不那么严谨但非常有用的类比：shader 像是 GPU 上的一条"流水线规章制度"。每个顶点进来，按规矩放到正确的位置；每粒像素（片元）进来，按规矩涂上正确的颜色。制度对所有顶点/像素一视同仁，不搞特例。

#### 1.4 渲染管线：从模型到屏幕的流水线
"顶点着色器"和"片元着色器"这两个名字我们已经提了好几次。但它们在什么时候执行？它们之间又发生了什么？要回答这个问题，需要了解**渲染管线（rendering pipeline）**。

渲染管线是 GPU 内部一条固定的流水线，它负责把"场景中有一个球、有一个光源、摄像机在某个位置"这样的描述，最终变成屏幕上几百万个像素的颜色。下图是这条流水线的极简版本：

[IMAGE: 渲染管线示意图](../ch01-diagrams/shader-flow.webp)

下面我们按顺序走一遍这七个步骤。每走一步，你都可以在脑海中想象一个简单的三角形正沿着这条流水线流动。

不过在进入流水线之前，我们需要先弄清楚"顶点"到底是什么。在 3D 图形学中，所有看得见的物体都由 **3D 网格（mesh）** 组成。一个网格包含两部分：**顶点（vertex）** 存储位置、UV 坐标、法线方向等信息；**面（face）** 定义哪些顶点连接成三角形。现代 GPU 只画三角形，所以一个复杂人物模型不过是几万个三角形的集合。你可以把网格想象成一张渔网——绳结是顶点，三个相邻绳结间拉紧的三角区就是面。所有三角面拼在一起，就是你看到的 3D 物体表面。顶点着色器接下来要处理的，正是这些绳结——每一个顶点，一个不漏。

**步骤 1：顶点输入（Vertex Input）**

游戏引擎把场景中所有需要渲染的物体的顶点数据打包发给 GPU。顶点数据包含什么？最少要有位置（这个顶点在空间中的坐标），如果有 UV 坐标、法线方向、顶点颜色等，也一起打包。在 Godot 中，这一步由引擎自动处理，你不需要手动操作——你只需要知道有这件事发生了。

**步骤 2：顶点着色器（Vertex Shader）**

GPU 对每一个顶点运行一遍顶点着色器。这个阶段的**唯一任务**是决定每个顶点最终出现在屏幕上的哪个位置。它接收顶点在模型空间中的原始坐标（在 Godot 中，这个变量叫 VERTEX），经过各种坐标空间变换（模型矩阵 → 世界矩阵 → 视图矩阵 → 投影矩阵——这些矩阵的事交给第 3 章细讲），最终输出这个顶点在裁剪空间中的坐标。

除此之外，顶点着色器也可以顺手做一些别的事——比如把法线方向、UV 坐标等数据打包传给后面的阶段。但它的核心职责始终是：**位置，位置，还是位置**。

这里有一个概念需要提前种下：顶点着色器传给后面阶段的数据，在 Godot 中，这套机制叫做 **varying**——你在顶点着色器中定义的 varying 变量，经过光栅化阶段的插值后，会在片元着色器中以插值后的值出现。简单说：顶点着色器在出口放一个值，片元着色器在入口收到一个经过三角形内部平滑过渡后的值。这是顶点和片元这两个"盲区"之间唯一的沟通渠道。

**步骤 3：图元装配（Primitive Assembly）**

GPU 拿到一堆处理好的顶点坐标后，按照模型文件里定义的顶点连接顺序，把这些离散的点连成三角形（或线段、点）。这一步叫"图元装配"——简单说就是把点连成面。

**步骤 4：光栅化（Rasterization）**

这是整个管线中最关键的一步，也是"并行魔法"发生的节点。

光栅化的任务是：对于每一个三角形，判断它覆盖了屏幕上的哪些像素，然后为每一个被覆盖的像素生成一个**片元（fragment）**。片元可以理解为"候选像素"——它携带了该位置的颜色候选值、深度值等信息，但只有通过后续深度测试和混合阶段的片元，最终才会成为屏幕上真正的像素。片元包含了该像素对应这个三角形所需要的所有信息——位置、UV 坐标、法线方向等，这些数据是从三角形的三个顶点的对应数据**插值**出来的。

为什么说"插值"很重要？假设一个三角形的三个顶点分别被顶点着色器赋予了 (x=0, y=0)、(x=100, y=0)、(x=50, y=100) 三个屏幕坐标，而且三个顶点分别带有 UV 坐标 (0, 0)、(1, 0)、(0.5, 1)。那么光栅化后，三角形正中心那个片元的 UV 坐标就是三个顶点的 UV 平均值——(0.5, 0.333)。这就是**片元插值（fragment interpolation）**。

关键细节：顶点着色器只运行了 3 次（三个顶点），但光栅化后生成了成千上万个片元。**从 3 到成千上万的膨胀，靠的就是插值**。

一个具体的例子能帮你建立直觉：假设三角形的三个顶点被顶点着色器分别赋予纯红 (1,0,0)、纯绿 (0,1,0)、纯蓝 (0,0,1) 的颜色，并把这些颜色传给片元着色器。光栅化后，三角形内部的片元会收到三个顶点颜色的插值——靠近红顶点的区域偏红，靠近绿顶点的区域偏绿，三角形正中心是三色均匀混合的灰。最终屏幕上显示的就是一个从红到绿到蓝平滑过渡的彩色三角形。这就是插值的威力：你只需要指定三个顶点的值，中间的一切由 GPU 自动填补。

**步骤 5：片元着色器（Fragment Shader）**

GPU 对每一个片元运行一遍片元着色器。这个阶段的**唯一任务**是决定这个片元最终显示什么颜色。

它接收光栅化阶段插值好的数据（UV 坐标、法线方向等），加上从 CPU 端传来的 uniform 数据（纹理、光照参数、时间等），经过一通计算，输出一个 RGBA 颜色值。在 Godot 的 canvas_item 类型中，这个输出变量叫 COLOR；在 spatial 类型中，对应的概念是 ALBEDO。

片元着色器是 shader 编程中**最常写也最有创造空间**的部分。你见过的所有材质效果——金属高光、玻璃折射、皮肤次表面散射、火焰噪声动画——本质上都是片元着色器里的数学计算。

**步骤 6：测试与混合（Testing & Blending）**

片元着色器算出了一个颜色，但 GPU 还不能直接把它画到屏幕上。它需要先过几道关卡：

- **深度测试（Depth Test）**：这个像素前面有没有别的东西挡住它？如果有，而且那个东西不透明，那这个片元就该被丢弃。
- **模板测试（Stencil Test）**：某些高级效果会用到模板缓冲区来"画区域蒙版"，这里不展开。
- **混合（Blending）**：如果这个片元是半透明的，它不能直接覆盖屏幕上已有的颜色，而是要按照混合模式（blend mode）和已有的颜色"掺"在一起。
**步骤 7：帧缓冲（Frame Buffer）**

最终幸存下来的颜色值被写入帧缓冲——一块显存中的内存区域，里面存储了屏幕当前帧每个像素的颜色。当一帧中所有物体都渲染完毕，帧缓冲的内容被送到显示器上，你看到了画面。

然后，下一帧开始，重复以上全部流程。每秒 60 遍。

#### 1.5 两个着色器的分工：一张表格说清楚
很多初学者把 vertex shader 和 fragment shader 混为一谈，是因为它们看起来都是"有一段 shader 代码，输入一些数据，输出一些结果"。但从上一节的管线流程中你应该已经看出，这哥俩的分工是泾渭分明的：

************************
|  | 顶点着色器（Vertex Shader） | 片元着色器（Fragment Shader） |
| 处理对象 | 每个顶点（一个模型几百到几万个） | 每个片元/像素（一帧几百万个） |
| 核心任务 | 决定顶点在屏幕上的位置 | 决定像素的颜色 |
| 关键输入 | 顶点位置（VERTEX）、法线（NORMAL）、UV 坐标 | 插值后的 UV 坐标、法线、uniform 数据 |
| 关键输出 | 裁剪空间中的顶点坐标（Godot 自动处理） | RGBA 颜色（COLOR / ALBEDO） |
| 典型应用 | 旗帜飘动、草丛摇曳、果冻形变、Billboard | 金属材质、发光效果、溶解、描边、后处理 |
| 运行次数 | 少（与顶点数成正比） | 极多（与屏幕像素数成正比） |

一个理解这两个着色器关系的经典比喻：**顶点着色器是"捏骨架的"，片元着色器是"涂皮肤的"**。骨架决定了形状，皮肤决定了外观。旗帜飘动是骨架在动（vertex shader 移了顶点位置），旗帜上的纹样和光影是皮肤在表现（fragment shader 算了颜色）。

一个重要的认知：**从 GPU 的角度看，渲染管线中始终存在顶点阶段和片元阶段**。在传统的 OpenGL/Vulkan 编程中，这两个阶段通常需要你分别编写独立的 vertex shader 和 fragment shader 并配对使用。在 Godot 中，这两个阶段被统一写在一个 .gdshader 文件的两个函数里——vertex() 和 fragment()。你可以只编写其中一个函数，未编写的部分由引擎使用默认实现（例如：不写 vertex() 则顶点坐标直接透传，不写 fragment() 则使用默认白色）。理解这一点后，后续所有章节的 shader 代码你都能看明白哪部分在"捏骨架"、哪部分在"涂皮肤"。

#### 1.6 Shader 在游戏中的应用
在玩家眼中，shader 的效果是无处不在的。下面是一个分类速览——你在玩游戏时可以对照着寻找它们的踪迹。

**① 材质表现**

你看到的一切物体表面质感——剑刃的金属反光、湿润地面的模糊倒影、玻璃杯的边缘折射、皮肤的半透明感——都是 shader 的材质计算。这类 shader 的核心是片元着色器中的光照模型计算：对每个像素，根据光源方向、法线方向、视角方向，算出一个"合理"的颜色。

**② 顶点动画**

你看到角色的披风在身后飘、草地在风中摇摆、果冻受到挤压后弹来弹去——这些都不是美术师逐帧做的关键帧动画，而是 shader 在顶点着色器里根据时间、位置和噪声，实时移动了模型的顶点。算十次和算一万个顶点，对 GPU 来说区别不大——这就是顶点动画的优雅之处。

**③ 角色特效**

受伤闪白、中毒变色、死亡后身体像沙一样消散、隐身时身体变得半透明带点波纹——这些"角色状态变化"的效果，几乎都是片元着色器里对颜色和透明度的数学操作。溶解效果 = 噪声图 + step() 判断；受伤闪白 = 原有颜色向白色插值。

**④ 屏幕后处理**

你看到的景深模糊（远处模糊近处清晰）、老电视的 CRT 扫描线和色差偏移、黑白电影滤镜、像素画风——这些效果不作用于单个物体，而是作用于"已经画好了的整幅画面"。它们读取当前帧的屏幕缓冲，做一些处理后再写回去。这就是后处理 shader。

**⑤ 风格化渲染**

卡通渲染（Cel Shading / Toon Shading）就是一种典型的风格化——把原本平滑的光照明暗过渡变成"三道色阶"的硬边效果，让 3D 画面看起来像 2D 动画。像素艺术渲染则反过来——把高清 3D 画面压成 16×16 分辨率再放大，制造复古感。这类 shader 的本质是"有意偏离物理真实的光照计算"。

**⑥ 程序化生成与数据可视化**

并不是所有 shader 都以"模拟材质"为目标。Shadertoy 社区 等创作者的实践展示了 shader 的另一面：用纯数学生成图像——程序化噪声地形、距离函数（SDF）绘制的几何图形、Ray Marching 渲染的 3D 场景、Mandelbrot 分形、HUD 雷达波形显示器、音频可视化频谱。这类 shader 的核心不再是"这个物体是什么材质"，而是"给定一个屏幕坐标，算出一个颜色"。

#### 1.7 Shader 在 Godot 中的挂载方式
在 Godot 中，shader 不能独立存在——它必须挂载在 **Material（材质）** 资源上，而 Material 又挂载在某个节点的材质属性上。这是 Godot 的资源层级：

```
节点（Node）
  └─ Material 属性（如 CanvasItem → Material）
       └─ ShaderMaterial（一种特殊的 Material）
            └─ Shader（.gdshader 文件）
```
具体到操作：

- 在场景中选中一个节点（比如 Sprite2D 或 MeshInstance3D）。
- 在 Inspector 面板中找到 **Material**（或 **Material Override**）属性。
- 点击属性右侧的下拉菜单，选择 **New ShaderMaterial**。
- 在 ShaderMaterial 的 **Shader** 属性中，点击下拉菜单，选择 **New Shader**。
- 在弹出的对话框中设置 shader 文件的保存路径，Godot 会自动创建一个 .gdshader 文件并在 Shader Editor 中打开。
创建 shader 文件后，Godot 会在文件头部自动加上一行 shader_type 声明。Godot 4.X 支持以下五种类型：

| shader_type | 认知定位 | 用途 | 常见挂载对象 |
| canvas_item | 2D 世界的着色器 | 2D 渲染（Sprite、UI、TileMap 等） | Sprite2D、ColorRect、TextureRect |
| spatial | 3D 世界的着色器 | 3D 渲染（网格、地形、天空之外的 3D 物体） | MeshInstance3D、CSG 节点 |
| particles | 粒子模拟 | GPU 粒子系统（控制粒子运动和行为） | GPUParticles3D、GPUParticles2D |
| sky | 天空渲染 | 自定义天空盒（替代默认天空） | Sky 资源 → Environment |
| fog | 体积雾渲染 | 自定义体积雾效果 | FogMaterial 资源 → Environment |

本书 90% 的内容围绕 canvas_item 和 spatial 两种类型展开：第 3 部分（2D 实战）全部使用 canvas_item，第 4 部分（3D 实战）全部使用 spatial。particles、sky、fog 属于特定场景下的专用着色器，将在第 5 部分（进阶专题）中涉及。

#### 本章小结
如果你只能从这一章带走一句话，请带走这条：**shader 是 GPU 上并行运行的微型程序——并行带来性能，也带来"看不见邻居、不记得过去"两条铁律**，后续章节里你看到的所有写法（用 uniform 传参、用 varying 在 vertex→fragment 间传值、避免 if 分支等等）几乎都是这两条铁律的副产物。

把本章要点压缩成一张地图：

- **概念地基**：CPU 串行并发 vs GPU 海量并行；渲染管线 6 步（顶点输入 → vertex → 图元装配 → 光栅化 → fragment → 帧缓冲）。
- **两种处理器**：vertex() 管"点在哪里"，fragment() 管"像素画什么颜色"——所有内置变量和矩阵都围绕这两件事展开。
- **Godot 入口**：shader 必须经 节点 → Material → ShaderMaterial → Shader(.gdshader) 这条资源链挂载；shader_type 决定能用哪些内置变量。
- **六类应用**：材质 / 顶点动画 / 角色特效 / 屏幕后处理 / 风格化 / 程序化生成——后续每一章都属于其中一类。
下一章（ch2）会补齐这套地基所需的数学工具：向量、点积、叉积、矩阵、齐次坐标。它们并不是新知识，而是把你在本章已经理解的关系"翻译成 GPU 能算的运算"。
