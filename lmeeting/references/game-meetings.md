# 游戏项目会议：按目的选方法

只读取并使用当前相关的段落。以下是对游戏项目的操作建议，不要求团队采用固定组织架构、会议频率或完整敏捷流程。

| 会议类型 | 核心问题 | 会末应有的结果 |
|---|---|---|
| 创意探索 | 为哪种玩家体验寻找可能性？ | 少量可比较的想法与优先验证的问题 |
| 玩法、系统、关卡、叙事或 UI 评审 | 方案是否产生想要的体验，规则能否完整执行？ | 保留、修改或否决的决定，以及原型或试玩任务 |
| 美术选型 | 哪种风格符合目标且能持续制作？ | 三个参考、统一风格、可验收小样 |
| 技术方案 | 哪个实现能满足约束并承担长期成本？ | 技术选择或试验任务、边界与依赖 |
| 排期与范围 | 在现有能力和依赖下，本阶段交付什么？ | 可验收范围、依赖顺序、计划与调整条件 |
| 进度与跨部门协调 | 什么正在阻碍共同目标，谁需要谁提供什么？ | 阻塞的承接人、依赖交付约定和下一步 |
| 试玩与缺陷评审 | 哪些体验问题或缺陷优先处理？ | 问题证据、优先级、修复或验证任务 |
| 里程碑验收 | 当前版本是否达到事先约定的完成条件？ | 逐项验收结果、未达标内容及处置 |
| 复盘 | 预期与实际为何不同，下一轮如何改善？ | 有证据的原因分析和少量可检查的改进 |

## 创意探索：先形成选项，再筛选

会前明确目标玩家、体验问题与确定的硬边界；不要一开始就把个人偏好当成限制。先独立提出想法，发散阶段只澄清含义，暂缓逐条争辩。

把想法写成“玩家在什么情境做什么，因此获得什么体验”，再按不同实现思路归类。进入收敛阶段后，才按客观条件筛选，比较价值和关键未知。避免只因新想法缺少历史数据就淘汰它；选择值得低成本验证的方向。

**主持问法**：“这些方案想解决的是同一个问题吗？”“哪种做法会带来明显不同的体验？”“我们先验证什么，就能判断它值不值得继续？”

**产出**：方案简述、预期体验、最大未知、验证方式及选取理由。探索会可以以确定下一轮试验结束，不强求当天定最终设计。

## 玩法与内容评审：用玩家过程检查规则

玩法、系统、关卡、叙事和 UI 共用这一方法，证据按对象选择。先对齐一个具体玩家情境，按“触发—玩家可选行动—成本与限制—结果与反馈—后续影响”走通；边界情况只挑可能改变结论的部分。

将“规则缺失或相互矛盾”“实现不符合设计”“符合设计但体验不佳”分开，分别补规则、修实现或验证设计。用目标玩家和产品阶段判断复杂度，不以开发者熟练度替代新玩家体验。

对于“太难、拖沓、没策略”，先查发生在哪一步，再区分信息不足、选择没有差异、反馈延迟或数值失衡等假设。表格计算可以排查规则和数量关系，实际节奏与理解成本仍要试玩。

**产出**：已确定规则、受影响依赖、未决体验假设、修改或原型任务及验收方式。美术专用的三个参考数量不套用到这里。

## 技术方案：比较约束与代价

由实际执行者说明当前能力和实现成本，比较候选的性能、工具支持、调试、维护、内容制作流程及整合依赖。只讨论与当前项目有关的维度，避免技术名词或流行程度代替判断。

“能写出来”与“在目标设备和内容规模下可靠运行”分开。争议在可行性时做有时间边界的技术试验，预先定义场景、数据量、测量方法与通过标准；不要只展示空场景峰值性能。

**产出**：选择理由、已接受的代价、接口和资源提供方、试验结果或任务。多模块或架构变更仍遵守项目确认要求；会议建议不能自动授权改代码。

## 排期与范围：从可验收成果反推工作

先决定阶段目标和完成条件，再由执行者拆出工作、估计范围和关键依赖。清点实际可用能力，包含整合、评审、测试与必要返工；工作量不能直接当自然日工期。

把内容分成“缺了就不能实现阶段目标”“可后移”“仅在有余量时做”，说明划分理由，不把所有需求都标为必做。先按交付先后排依赖，识别一个环节延误会卡住哪些成果；不能假设多人工作可以无限并行。

目标、期限和资源发生冲突时，把缩小范围、改变实现、调整顺序或修改期限的代价摆出来，由对应负责人决定。新需求进入时说明替换什么或增加什么投入；不能默认靠加班填补未知。

**产出**：本阶段交付范围、负责人、依赖、估计假设、预计时间和触发调整的条件。未经确认的估计不写成承诺。

## 进度与跨部门协调：围绕阻塞和交接

普通状态更新可以会前写明，会中优先处理“目标偏差、未完成依赖、需要帮助、需要决策”。没有差异和阻塞时可以提前结束，不要求人人重复汇报已完成事项。

交接按“谁向谁提供什么，提供哪个版本，何时需要，接收方如何验收”说清。策划规则、程序接口、美术资源和测试环境分别确认输入与验收条件；不能用“差不多了”代表可整合。

需要少数人深入排查的问题，明确参与者和下一次反馈时间后转小范围处理；影响全局范围或日期的结论再带回。

**产出**：阻塞描述、影响、承接人、所需输入和处理时点。协调完成不等于阻塞已经解决。

## 试玩与缺陷评审：先记录发生了什么，再判断怎么改

试玩材料包含版本、目标玩家特征、任务、设备、观察与玩家原话。将“观察到的行为”“玩家感受”“团队原因解释”“建议修改”分列。不要用“是不是太难了”一类暗示性问法替代开放追问，也不要只收集能支持现有方案的反馈。

**主持问法**：“当时你想做什么？”“你以为操作后会发生什么？”“在哪一刻开始觉得拖沓？”报告人数和测试条件；小样本不推导全体玩家比例，内部测试不冒充目标用户验证。

体验问题按核心流程影响、出现情境、证据强度和验证成本排序。缺陷则另看严重程度、复现频率、影响范围、是否有绕行办法及是否阻塞交付；业务优先级与缺陷严重程度分开记录，不能只先修容易修的。

**产出**：问题清单、证据和缺项、优先级理由、修复或验证任务。尚未复现不等于问题不存在；与设计一致但体验差也应留下后续处理。

## 里程碑验收：按事先约定的标准看实际版本

用指定版本和实际交付物逐项核对已有完成条件。区分“单项完成”“已整合”“已验证”，展示视频或口头声明不能自动证明可玩版本合格。

未达到条件的如实列出。若标准本身需改变，记录有授权者的变更决定及影响，不能现场降低标准后追认原计划已完成。有条件接受要写明剩余项、责任人、期限及限制。

**产出**：每项的通过、未通过或未验证状态，整改安排及下一阶段是否能进入的明确依据。验收通过不自动授权发布。

## 复盘：还原过程，选择少量可检查的改善

先对照“原本预期—实际发生—影响”，按记录和时间线补齐事实，包含有效做法。再追查当时的信息、流程、工具、依赖和决策条件；避免事后假定参与者早就知道结果。

不把“某人不认真”作为分析终点；可以明确具体动作和改进责任，但要继续找如何降低再次发生的机会。因果关系不确定时保留假设，允许多个因素共同作用。

每轮优先选少量影响大且可执行的改进，建议先取一至三项，再按团队能力调整。写成改变什么、谁实施、下轮看什么证据。检查上轮改进是否实施、有没有效果，避免年年重复同一结论。

**产出**：事实与原因、继续保留的有效做法、改进任务、复查时点。会议中的改进建议未经授权不自动修改团队制度。
