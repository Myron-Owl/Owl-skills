# 第 11 章：Shader 预处理器与工程化

### 第 11 章：Shader 预处理器与工程化 —— 从单文件到模块化工程
**学习目标**：掌握 #define、#include、#ifdef、#if 等预处理指令，能够将前面章节学过的函数抽成 .gdshaderinc 共享库，用条件编译控制特效开关，按 Godot 官方代码风格规范撰写可维护的 shader 工程。

**场景搭建**：本章需要两个 shader 文件 + 一个 shared library 文件。第一个 shader 是 canvas_item 类型。不需要 GDScript 脚本，所有效果在 shader 内完成。

**内容要点**：
- #define 宏定义：常量替换、宏函数
- #ifdef / #ifndef / #endif：最简条件编译——有选择地包含代码段
- #if / #elif / #else：条件编译链——精细的多分支控制
- #include "path/file.gdshaderinc"：复用公共函数库——一次编写，多处引用
- #ifndef 头文件保护（include guard）：防止重复包含
- 内置宏：RENDERER_FORWARD_PLUS / RENDERER_MOBILE / RENDERER_COMPATIBILITY——按渲染器执行不同代码路径
- 实战 ：把 ch7 的噪声函数抽到 noise.gdshaderinc，用 #include 在shader 中使用
- Godot 官方 Shaders style guide 核心规范（Tab 缩进、命名规范、代码顺序、clang-format 配置）

#### 11.1 为什么你的 shader 需要一个"预处理器"
前 10 章你写的所有 shader 都有一个共同特点：所有代码写在一个 .gdshader 文件里——从 shader_type 声明到底层 hash 函数、从噪声计算到颜色映射，全都堆在一起。

这在写单个效果时没问题。但当你开始写第二个、第三个 shader 时，问题出现了：

**同一个 hash() 函数你抄了三遍。同一个 smoothstep 封装抄了四遍。改了其中一个 bug，剩下的三个你还得记得改。**

这就是软件工程中最古老的问题——**代码复用**。更具体地说，shader 编程中面临三个工程化需求：

- **共享函数库**：多个 shader 需要同一个噪声函数、同一个颜色转换函数、同一段数学工具代码——能不能写一次、到处引用？
- **效果开关**：同一个 shader 想在不同场景下"打扮不同"——在 mobile 上不加 Fresnel（省钱），在 desktop 上加满效果——能不能不改代码、只改一行 #define 就切换？
- **渲染器适配**：同一个 shader 在 Forward+ 和 Mobile 渲染器下行为不同——能不能让 shader 知道自己跑在哪个渲染器上？
这三个问题的答案，就是 Godot Shader 的**预处理器（preprocessor）**。

**预处理器是什么？** 在 shader 代码交给 GPU 编译器之前，Godot 引擎先运行一轮"文本级别的预处理"——# 开头的指令在这一步被展开为shader代码。GPU 编译器收到的已经是展开后的完整源码，看不到任何 #define 或 #include 痕迹。预处理器 = 给 shader 加了一层"编译前的文本工具层"。

Godot Shader 的预处理器支持以下指令：

| 指令 | 作用 | 类比 |
| #define KEY VALUE | 文本替换 | 全局查找替换 |
| #define MACRO(args) body | 带参数的宏函数 | 内联代码生成 |
| #include "path.gdshaderinc" | 插入外部文件内容 | C 语言的 #include |
| #ifdef KEY / #ifndef KEY | 检查某个宏是否定义过 | if (defined(KEY)) |
| #if COND / #elif / #else | 数值条件分支 | if (value > 0) |
| #endif | 结束一个预处理块 | 闭合括号 |

#### 11.2 #define：文本替换——shader 里的"缩写"

##### 11.2.1 它是什么？
#define 做一件事：在编译前，把代码中出现的某个名字替换成你指定的文本。替换发生在"预处理"阶段——GPU 编译器根本不知道有 #define 这回事，它看到的只有展开后的代码。

##### 11.2.2 为什么需要它？
三个典型场景：

- **常量集中管理**：MY_GOLD 出现在 8 个地方，想改成更暖的金色？只改一行 #define。
- **代码可读性**：#define PI 3.1415926 比满屏的 3.1415926 好读。
- **跨平台适配**：不同平台用不同精度常量，#define 一行切换。

##### 11.2.3 怎么用：最简形式

```
#define GOLD vec3(1.0, 0.84, 0.0)
#define ANIMATION_SPEED 2.5

shader_type canvas_item;

void fragment() {
    vec3 color = GOLD;
    color *= sin(TIME * ANIMATION_SPEED) * 0.5 + 0.5;
    COLOR = vec4(color, 1.0);
}
```
预处理后，GPU 收到的代码是：

```
void fragment() {
    vec3 color = vec3(1.0, 0.84, 0.0);
    color *= sin(TIME * 2.5) * 0.5 + 0.5;
    COLOR = vec4(color, 1.0);
}
```
GOLD 和 ANIMATION_SPEED 已经不存在了——它们被逐字替换为定义的值。

##### 11.2.4 带参数的宏函数
#define 不只是值的替身，还能定义带参数的"宏函数"。TGSB 配套代码中有一个典型例子——用 #define 包装 3D 旋转矩阵：

```
#define RX(a) mat3(             \
    vec3(1, 0, 0),              \
    vec3(0, cos(a), -sin(a)),   \
    vec3(0, sin(a), cos(a)))
```
使用 RX(0.5) 会被预处理器直接展开为完整的 mat3(...) 表达式。这比另写一个 mat3 rotate_x(float a) 函数更"轻"——宏展开不产生函数调用开销。

宏函数是原样替换的，所以会有一个括号陷阱。例如：

```
#define SQUARE(x) x*x
SQUARE(a+b)
```
展开后的结果是：

```
a+b*a+b
```

而不是你想像的

```
(a+b)*(a+b)
```

**宏函数 vs 普通函数的选择**：宏函数展开后直接嵌入调用处，没有函数调用栈，但也不做类型检查——传错了参数不会报错，只会产生奇怪的展开结果。一般情况下，**能用普通函数就不要用宏函数**。

#### 11.3 条件编译：#ifdef 与 #endif —— 让编译器帮你"删代码"

##### 11.3.1 它是什么？
#ifdef FOO 读作"如果定义了 FOO"，它告诉预处理器：**如果 FOO 这个宏存在，就保留下面的代码；如果不存在，就把下面到 #endif 之间的代码全部删掉**。

##### 11.3.2 为什么需要它？
假设你在写一个 shader 同时用于游戏中的"高低画质"两档：
- 高画质版本：需要 Fresnel 边缘光 + 法线贴图 + 6 层 FBM 噪声
- 低画质版本：只要基础颜色 + 2 层噪声

如果没有条件编译，你需要维护**两个独立的 shader 文件**。当你要修一个共用的 hash() 函数的 bug 时，需要改两个文件。条件编译让你**一个文件搞定两套效果**，改 bug 只需改一次。

##### 11.3.3 怎么用：最简条件编译

```
#define HIGH_QUALITY

shader_type canvas_item;

void fragment() {
    vec3 color = vec3(0.2);

#ifdef HIGH_QUALITY
    // 只有定义了 HIGH_QUALITY 时，这段代码才存在
    color += texture(some_detail_map, UV * 5.0).rgb;
#endif

    COLOR = vec4(color, 1.0);
}
```
当你 #define HIGH_QUALITY 时，texture 那行代码被保留。当你删掉（或注释掉）这行 #define 时，texture 那行代码在编译前就被预处理器移除——GPU 编译器根本看不到它，不消耗任何指令。

这正是条件编译区别于运行时 if 的关键：运行时 if 消耗 GPU 指令（即使分支不执行，代码仍占用指令缓存，且 GPU 线程束可能两边都执行一遍）。预处理器 #ifdef 在编译前就把代码物理删除了——零开销。

##### 11.3.4 #ifndef：反过来的判断
#ifndef FOO 的逻辑正好相反——"如果没有定义 FOO，才保留下面的代码"。最常见的用途是**头文件保护（include guard）**：

```
#ifndef MY_LIBRARY
#define MY_LIBRARY

// 库的所有代码放在这里
float my_func(float x) {
    return x * x;
}

#endif
```
为什么需要这个？假设你的 shader A 包含了 noise.gdshaderinc，shader B 也包含了它，而 shader C 同时包含了 A 和 B——如果不做保护，noise.gdshaderinc 就会在 C 中被插入两次，导致函数重复定义报错。有了 #ifndef / #define / #endif 三重保护，第二次 #include 时 MY_LIBRARY 已经定义过，整个文件内容被跳过。

#### 11.4 条件编译链：#if / #elif / #else —— 不只"是"和"否"

##### 11.4.1 它是什么？
#if COND 做数值判断——COND 是一个整数表达式（只在预处理阶段有效），根据结果决定保留哪段代码。#elif 和 #else 提供多分支选择。

##### 11.4.2 为什么需要它？
#ifdef 只能判断"有没有定义"，不能判断"定义的值是多少"。但实际场景中你需要精细的分级控制：

```
#define QUALITY 2   // 低=0（手机）、中=1（Switch）、高=2（PC）
```
你不能用 #ifdef QUALITY 来区分这三档——QUALITY 总是"定义过"的。你需要 #if QUALITY >= 2。

##### 11.4.3 怎么用：多档画质切换

```
#define QUALITY 2

shader_type canvas_item;

void fragment() {
    vec3 color = vec3(0.0);

#if QUALITY >= 2
    color += apply_fresnel(NORMAL, VIEW, 3.0);
#elif QUALITY == 1
    color += apply_fresnel(NORMAL, VIEW, 1.0);
#else
    color += base_color_only();
#endif

    COLOR = vec4(color, 1.0);
}
```
当 QUALITY 为 2 时，GPU 编译器只看到 apply_fresnel(NORMAL, VIEW, 3.0)。为 1 时看到弱化版。为 0 时看到 base_color_only()。**三段代码永远只有一段存在于最终编译中。**

**既然 Shader 已经有 uniform bool，为什么还要用 #if？**

实际上，两者解决的是**完全不同层次**的问题。**#if 用来决定"编译哪些代码"，uniform bool 用来决定"运行哪些代码"。**一般来讲在配置时用 #if，游戏中状态切换用 uniform bool。

#### 11.5 #include：把你的函数库"贴"进来

##### 11.5.1 它是什么？
#include "path/file.gdshaderinc" 把指定文件的**全部内容**原样插入到这一行的位置。它支持相对路径和res://绝对路径。

##### 11.5.2 为什么需要它？
回到本章开头的场景：你在 ch7 写了 hash()、noise_2d()、fbm() 等函数。你想复用这些噪声函数时，没有 #include要把同一套函数抄三遍。发现 bug 要改三个地方。有了 #include就只需要把函数写在一个 .gdshaderinc 文件中，三个 shader 各自引用一行 #include。改 bug 只改一个文件。这就是**"一次编写，多处使用"**。

##### 11.5.3 .gdshader vs .gdshaderinc：什么时候用什么？
****
| 文件类型 | 扩展名 | 用途 | 可否直接挂 Material |
| 着色器文件 | .gdshader | 独立的 shader，含 shader_type 声明 | ✅ |
| 着色器包含文件 | .gdshaderinc | 被 #include 引用的库，不含 shader_type | ❌ |

.gdshaderinc 不应该有 shader_type 声明——它只是函数/宏/常量的"零件包"。Godot 编辑器会自动识别 .gdshaderinc 扩展名并将其高亮为 shader 语言。

##### 11.5.4 路径规则
#include 的路径相对于**引用它的 .gdshader 文件**所在的目录计算。例如：

```
project/
├── shaders/
│   ├── my_material.gdshader       ← #include "lib/noise.gdshaderinc"
│   └── lib/
│       └── noise.gdshaderinc
```
如果 .gdshaderinc 在项目根目录的 shared/ 下，而 shader 在 characters/enemy/ 下：

```
project/
├── shared/
│   └── noise.gdshaderinc
├── characters/
│   └── enemy/
│       └── enemy_shader.gdshader  ← #include "../../shared/noise.gdshaderinc"
```
两层 ../ 向上回到项目根目录，再进入 shared/。Godot 编辑器支持路径自动补全——输入 #include " 后按 Ctrl+Space 会弹出文件选择面板。

#### 11.6 实战 ：抽噪声函数到共享库
现在把 ch7 的核心代码——hash()、noise_2d()、fbm()——从单文件 shader 中"提"出来，放进一个 .gdshaderinc。然后写一个 shader 来引用它：

**共享库**：noise.gdshaderinc

```
#ifndef NOISE_LIB
#define NOISE_LIB

float hash(vec2 p) {
    ivec2 i = ivec2(p);
    int n = i.x * 73856093 ^ i.y * 19349663;
    n = n * 1664525 + 1013904223;
    n = n ^ (n >> 16);
    return float(n) * (1.0 / 2147483647.0);
}

float noise_2d(vec2 p) {
    vec2 i = floor(p);
    vec2 f = fract(p);
    f = f * f * (3.0 - 2.0 * f);

    float a = hash(i);
    float b = hash(i + vec2(1.0, 0.0));
    float c = hash(i + vec2(0.0, 1.0));
    float d = hash(i + vec2(1.0, 1.0));

    return mix(mix(a, b, f.x), mix(c, d, f.x), f.y);
}

float fbm(vec2 p, int octaves) {
    float value = 0.0;
    float amplitude = 0.5;
    float frequency = 1.0;

    for (int i = 0; i < 6; i++) {
        if (i >= octaves) break;
        value += amplitude * noise_2d(p * frequency);
        frequency *= 2.0;
        amplitude *= 0.5;
    }

    return value;
}

#endif
```
噪声驱动的动态雾气 shader

```
shader_type canvas_item;

#include "include/noise.gdshaderinc"

uniform float flow_speed = 0.2;
uniform float fog_density = 0.6;

void fragment() {
    vec2 uv = UV + vec2(TIME * flow_speed, 0.0);
    float n = fbm(uv * 5.0, 3);
    float alpha = n * fog_density;
    COLOR = vec4(vec3(0.8, 0.85, 0.9), alpha);
}
```

#### 11.7 内置渲染器宏：让 shader 知道自己在哪个渲染器上跑
Godot 4.x 有三个渲染后端：Forward+（桌面高端）、Mobile（移动端/低端）、Compatibility（兼容老硬件）。它们在 depth buffer、光照模型、纹理处理等方面有差异。

Godot 在编译 shader 时会自动定义以下宏之一：

| 宏名 | 渲染器 | 典型场景 |
| RENDERER_FORWARD_PLUS | Forward+ (Vulkan) | 桌面 PC、主机 |
| RENDERER_MOBILE | Mobile (Vulkan) | 手机、Switch |
| RENDERER_COMPATIBILITY | Compatibility (OpenGL) | 老硬件、Web 导出 |

你可以在 shader 中用这些宏做渲染器适配，以下是官网的一个使用示例：

```
shader_type spatial;

void fragment() {
#if CURRENT_RENDERER == RENDERER_COMPATIBILITY
    ALBEDO = vec3(0.0, 0.0, 1.0);
#elif CURRENT_RENDERER == RENDERER_MOBILE
    ALBEDO = vec3(1.0, 0.0, 0.0);
#else // CURRENT_RENDERER == RENDERER_FORWARD_PLUS
    ALBEDO = vec3(0.0, 1.0, 0.0);
#endif
}
```

#### 11.8 官方 Shaders Style Guide 核心规范
写完预处理器的工程结构后，还需要一套**代码风格规范**来保证你的 shader 可读、可维护。Godot 官方提供了 [Shaders style guide](https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/shader_style_guide.html)，以下摘录核心建议：

##### 缩进：只用 Tab
Godot 编辑器的 shader 部分**默认使用 Tab 缩进**。不要混用空格——编辑器可能把代码格式化错。主流 Godot 开源项目（GDQuest、VesperaFX、eldskald-cel）全部使用 Tab。

##### 代码顺序（从上到下）
一个整洁的 .gdshader 文件按以下顺序组织：

```
1. shader_type 声明
2. render_mode（如有）
3. #define 宏定义
4. #include 包含文件
5. group_uniforms 块（如有）
6. uniform 变量
7. varying 变量
8. 自定义函数
9. vertex() 处理器
10. fragment() 处理器
11. light() 处理器（仅 spatial）
```

##### 命名规范

| 元素 | 规范 | 示例 |
| uniform | snake_case | noise_scale、fresnel_power |
| varying | UPPER_SNAKE_CASE | SPECULAR_COLOR |
| 自定义函数 | snake_case | hash()、apply_fresnel() |
| 常量 (const) | UPPER_SNAKE_CASE | MAX_OCTAVES、PI |
| #define 宏 | UPPER_SNAKE_CASE | USE_FRESNEL、GOLD |

Godot 编辑器内置了 shader 格式化：在 shader 编辑器中按 Ctrl+Alt+F（macOS: Cmd+Option+F）即可自动格式化当前文件。

#### 本章小结
回顾本章学到的所有预处理指令及其组合方式：

```
#define GOLD vec3(1.0, 0.84, 0.0)
        └── 常量/宏函数替换

#define USE_EFFECT 1
#ifdef USE_EFFECT
    // 效果代码
#endif
        └── 条件编译——开关特效

#if USE_EFFECT == 1
    // 分支 A
#elif USE_EFFECT == 2
    // 分支 B
#else
    // 默认
#endif
        └── 条件编译链——多档控制

#ifndef MY_LIB_GUARD
#define MY_LIB_GUARD
    // 函数库全内容
#endif
        └── include guard——防止重复包含

#include "shared/noise.gdshaderinc"
        └── 模块复用——一次编写，全项目共享

#define USE_EFFECT 1
#ifdef USE_EFFECT
#include "effects/effect.gdshaderinc"
#endif
        └── 条件 include——按需加载模块
```
