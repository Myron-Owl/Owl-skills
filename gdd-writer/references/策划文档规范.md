## 1. 概述与使用方式

> 目标：策划文档由 AI 完成初稿 → 策划手动调优 → AI 一致性检查。
> 核心原则：**AI 写内容，人做决策。**

### 1.1 本文档只有一份，读者分两边

本文档不拆成两份文件，但内部明确分成两个区域，各读者各取所需：

| 区域 | 内容 | 谁读 |
|------|------|------|
| 正文（第 1–8 节） | 策划写文档、审文档要遵守的全部规则 | 策划日常阅读，也是本文档的主体 |
| 附录 A：AI 执行细则 | 供 AI 生成与自查的执行细节、格式速查和检查单 | 策划平时不必通读，只在审稿对表时查阅；需要理解"AI 被如何约束"的程序或后续 AI 也看这里 |

正文只写"是什么、为什么、怎么做才对"，不出现面向机器的命令句；机器必须执行的细节统一收进附录 A。正文与附录 A 不重复定义同一条规则——附录只引用正文编号或补充执行细节。

### 1.2 一条铁律

> **只写具有信息增量，且省略后会产生实际分歧的内容。**

每句话必须同时通过两道门槛：

1. **信息增量**：不能从标题、相邻规则、公式、图表、配置字段、全局约定或引用文档直接推出。
2. **省略后果**：删除后会导致两种以上合理的设计、实现或验收结果，或者会丢失已确认的例外与关键取舍。

"能够验证"或"与实现有关"不足以证明一句话值得保留。所有合理实现都会采用的默认行为、不说也不会产生不同结果的常识、没有现实发生路径的假想问题，均不写入正文。拿不准时先删除；评审能指出具体分歧或实际风险后再补回。

### 1.3 三条支撑原则

- **AI 写、人调优**：YAML 头部、初稿由 AI 生成，策划负责核对和决策（见[第 6 节](#6-版本状态与确认流程)的确认规则）。
- **单一事实源**：同一概念只在最适合查找的位置完整定义一次。其他位置只有在不引用会导致误读时才放链接或一句引用，不换词重写，也不为维持章节完整而重复。
- **设计推理要留痕**：文档不只记录"做了什么"，关键取舍要写下"为什么这么做"（见[4.9 节](#49-去重精简与设计理由)），供程序理解、供后续接手者和复盘参考。

## 2. 新文档启动清单

新写一篇文档时按顺序过一遍；大部分步骤的详细规则见括号内章节：

1. 按[文件命名规则](#31-文件命名规则)创建文件（`{作者缩写}_{文档名称}{YYYYMMDD}.md`）。
2. 复制[第 7 节的 system 模板](#72-system系统设计模板)（其他类型看[差异表](#73-其他类型的章节差异)），填写 YAML 头部，`ai_context` 必填。
3. 概述只写一句话定位和核心目标，控制在 2～5 条短句内（见[4.4 节](#44-概述怎么写)）。
4. 按功能模块组织规则正文，标题写清具体内容，规则直接跟在标题下，用"条件 → 行为 → 结果"的顺序（见[4.1 节](#41-功能模块与标题层级)）。
5. 需要图示时按[图示使用判定](#52-图示使用判定)决定，用 draw.io 制作并把 `.drawio` 源文件和导出的 `.png` 一起放进公共 `img/` 目录（见[5.1 节](#51-制图纪律)）。
6. 界面和流程只在通过信息增量与省略后果两道门槛时添加；没有界面、或单次操作直接出结果时不要硬凑（见[4.2 节](#42-规则界面流程三个切面)）。
7. 逐句执行反事实删除：删掉后是否仍只有一种合理结果？如果是，删除；再检查同一事实是否只定义了一次（见[4.9 节](#49-去重精简与设计理由)）。
8. 拿不准的关键数值、方案或归属，不要写进文档，回对话里问（见[6.4 节](#64-未确认内容与提问规则)）。
9. 完成后把 `status` 改为下一阶段、修订序号加 1，并在更新记录里追加一行（≤30 字）。

## 3. 文件与文档骨架

### 3.1 文件命名规则

每篇文档的文件名包含**谁写的 + 写什么 + 什么时候写**，方便在文件列表里一眼认出。

```text
{作者缩写}_{文档名称}{YYYYMMDD}.md
```

> **说明**：`{ }` 表示待替换的占位符，模板和示例中的占位符在使用时替换为真实内容；正文成品不得遗留读者无法判断含义的花括号占位符。

- **作者缩写**：策划姓名拼音首字母，小写，例如 `lm`、`myron`。
- **分隔符**：作者缩写后用下划线 `_`，例如 `lm_`。
- **文档名称**：中文，不超过 10 个字，例如 `势头系统`。
- **日期**：8 位数字紧接文档名，不加分隔符，例如 `20260706`。
- **扩展名**：统一 `.md`。
- **规范基线文件例外**：项目根目录的 `策划文档规范.md` 使用固定文件名，不添加作者缩写和日期；其他策划文档一律按上述格式命名。

正确示例：

- `lm_势头系统20260706.md` → 路人甲 2026年7月6日 创建
- `myron_命中系统20260705.md` → Myron 2026年7月5日 创建

常见错误：

- `20260706_势头系统.md`：日期不能放在文件名开头。
- `势头系统.md`：缺少作者缩写，看不出负责人。
- `lm_ 势头系统 20260706.md`：文件名不能包含空格。

### 3.2 YAML 头部

每篇文档最顶部是一块"身份证"信息，即两行 `---` 之间夹着的 YAML。YAML 由 AI 生成，策划负责核对。其中 `ai_context` 是**本文档写给 AI 的生成与维护约束**——它集中承载所有面向机器的指令，正文不再散布 AI 指令。

```yaml
---
title: 文档标题
type: 文档类型          # system / world / narrative / data / guide
status: 初稿 | 调优中 | 已定稿 | 已废弃
version: 版本号
updated: YYYY-MM-DD
author: {AI名称}+{作者缩写}  # 例：Claude+lm
ai_generated: true | false
dependencies:         # 可选：依赖的其他文档
  - 路径/文件名.md
ai_context: |         # 必填：本文档写给 AI 的生成与维护约束
  {生成约束、参考文档、必须检查、风格要求}
tags: [标签1, 标签2]
---
```

字段说明：

| 字段 | 必填 | 含义 |
|------|------|------|
| `title` | ✅ | 文档标题，不含版本号；版本只写在 `version` 和更新记录中 |
| `type` | ✅ | 文档类型：系统设计 / 世界观 / 叙事文案 / 数值数据 / 规范指南 |
| `status` | ✅ | 文档所处阶段：初稿 / 调优中 / 已定稿 / 已废弃 |
| `version` | ✅ | 版本号，格式"主版本号.修订序号"；修订序号逐次加 1，主版本号只在策划口头确认后修改 |
| `updated` | ✅ | 最后更新日期 |
| `author` | ✅ | 谁写的 + 谁负责的，例：`Claude+lm` |
| `ai_generated` | ✅ | true = AI 写的 / false = 人写的 |
| `dependencies` | 建议填 | 本文档参考了哪些其他文档（AI 生成时自动读取作为上下文）；暂无依赖时省略该项，禁止写占位引用 |
| `ai_context` | ✅ | 给 AI 的生成指导（写法见[附录 A.3](#a3-ai_context-怎么写)）；新文档不得省略 |
| `tags` | 建议填 | 搜索标签，方便以后找文档 |

`ai_context` 的展开版内容如果较长（涉及多个必须检查项、多篇参考文档），可以放在文末的"附录：AI 生成说明"模块（见[7.2 节](#72-system系统设计模板)），YAML 中保留摘要。

### 3.3 固定前置顺序

YAML 之后，标题、目录、更新记录、正文必须按下述顺序排列；任何说明、引用块或分隔线都不能插在它们之间：

```markdown
# 文档标题

## 目录

{正文一级章节目录}

## 更新记录

{更新记录表}

## 1. 概述
```

- H1 标题和 YAML 的 `title` 都不带版本号。
- 目录紧跟 H1 标题；更新记录紧跟目录。
- 目录与更新记录属于前置信息，不占用正文编号。
- 正文从 `## 1. 概述` 开始编号；附录不编号，用"附录 A / B / C"标识。
- 目录里可以列出附录入口，但附录链接属于目录内容，不要单独用 `## 附录` 标题夹在目录与更新记录之间。

### 3.4 正文编号规则

- `##` 是全文大模块，必须使用一级编号，例如 `## 2. 新文档启动清单`。
- `###` 是模块下的小节或功能模块，必须使用对应的二级编号，例如 `### 3.1 文件命名规则`。
- `####` 及以下不编号；标题层级最多用到 `#####`。更细的内容用加粗短标签、列表或代码块表达，避免目录过深。
- 同级标题必须按同一分类维度划分，例如都按"功能"或都按"数据类别"；不能把"队伍管理""数据来源""异常处理"这类不同维度的内容并列在同一级。

## 4. 正文写作规则

策划文档的目标不是把信息全部写进去，而是让程序、美术、UI 和后续接手者能按同一条阅读路线快速找到答案。本节是人读正文的核心规则；对应给 AI 的执行细节见附录 A。

### 4.1 功能模块与标题层级

正文以功能模块为组织单元。数字编号帮助读者在目录中定位，标题级别表达包含关系——两者同时使用，正文至少保证两级编号（`##` 一级、`###` 二级）。

- 功能模块标题必须说明具体主题，例如 `### 2.1 队伍管理`。
- **规则正文默认直接跟在模块标题下**，禁止使用 `#### 规则` 这类不说明内容的独立小标题。
- 同一 `##` 下有两个及以上可独立查找的功能模块时，必须用 `###` 拆分，不能堆在父标题下用长列表区分。
- 一个 `###` 模块下只有一小段内容且不存在同级模块时，不要为了形式硬拆标题。
- 列表只描述当前标题下的并列规则或步骤，不能代替功能模块的划分。
- 模块内容复杂、确需分隔时，使用 `**触发条件：**`、`**限制：**`、`**结果：**` 这类**具体的加粗短标签**，不再新增标题层级。

### 4.2 规则、界面、流程三个切面

规则、界面、流程各自承担不同信息，写作前先为每条信息指定唯一的主要归属：

| 切面 | 负责内容 | 不重复内容 |
|------|----------|------------|
| 界面 | 元素位置、显示内容、可见状态、玩家能识别的反馈 | 计算规则、后台处理顺序、完整页面流转 |
| 规则正文 | 条件、限制、阈值、优先级、允许与禁止、结果判定 | 控件位置、操作步骤、总体流程已定义的跳转 |
| 流程 | 有先后关系的玩家操作、系统动作、数据变化与异常收尾 | 静态显示、已完整定义的条件和判定 |

同时存在规则、界面和流程时，按 **规则正文 → 界面 → 流程** 排列；任何部分没有新增信息就删除。判断方法：

- **只有静态展示**：只写界面。
- **单次操作直接产生结果**：在界面表或规则中用一句话写明结果，不单列流程。
- **存在权限、阈值、优先级或状态判断**：直接写在具体功能标题下的规则正文里。
- **存在两个以上有意义的连续处理步骤、数据变化或异常收尾**：才增加流程。
- **没有界面的后台逻辑**：只写规则正文或流程。
- 只有单一控件的简单界面可以不单独放图，在规则或流程里直接描述。
- 无界面交互的纯数值规则（属性体系、伤害公式等）不套界面模板，直接在功能标题下写规则和公式。

切面划分不能把一个事实扩写成三种说法。某条信息在主要归属中已经完整定义后，其他切面不得再以同义句补齐；即使表达角度不同，只要不会改变结果，仍视为重复。

**同一界面在一篇文档中只完整展示和说明一次**；其他模块复用时链接到首次定义处，只补充差异。一个功能只有一个子流程时，直接放在 `#### 流程` 下，不再嵌套 `#####`；多个独立子流程（如入队、离队）才用 `#####` 分组。

### 4.3 格式选择：列表优先，表格三问

根据内容选择最短且不会引起误读的格式：

1. **自然段**：需要连贯阅读的结论、背景或必要设计理由。
2. **无序列表**：并列规则、条件、注意事项和检查项。
3. **有序列表**：存在先后关系的操作与处理流程。
4. **表格**：只有信息必须按固定列横向对照时才使用。

写表格前依次判断：

1. 读者是否需要在同一维度上横向比较多项内容？
2. 列名是否稳定，每一行是否都能按相同结构填写？
3. 改成列表后，信息是否会明显更难查找或更容易误读？

三个问题至少一个明确回答"是"，才使用表格；拿不准时默认用列表。默认不用表格的场景：只有"名称 + 一段解释"的简单说明、单一对象的属性介绍、有时间顺序的交互步骤、两三个差异点的横竖版说明、为了让版面整齐而做的两列表格。

**程序数据表不受"少用表格"限制**，但应明确标注为"配置表示例""存档字段"或"数据结构参考"，让读者能与普通规则说明区分开。更新记录、数值表这类本身是结构化数据的固定内容也直接用表格。

### 4.4 概述怎么写

概述用于建立最小且完整的整体认识，不承担详细论证。默认只写：

- **一句话定位**：这个系统是什么？
- **核心目标**：解决什么问题或产生什么效果？

总计控制在 2～5 条短句内。以下内容仅在能提供新增信息时填写：**设计思路**（设计不直观、存在重要取舍或易被错误修改时）、**玩家体验目标**（能约束具体规则或反馈时）、**使用场景**（使用者、触发时机或环境会影响规则时）。内容重合时必须合并，不得换词重复。

```markdown
## 1. 概述

> **一句话定位**：佣兵之家是玩家管理队伍和待命佣兵的统一入口。

**核心目标：**让玩家在进入战斗前集中完成队伍调整，并立即看到操作结果。
```

### 4.5 公式与代码块写法

公式、配置、数据结构、格式示例这类需要复制或看清结构的内容放进代码块，并填写正确的语言标记（`markdown` / `csharp` / `json` / `yaml` / `ini` / `text`，各自适用场景见[附录 A.1](#a1-语言标记与键值格式速查)）。要点：

- **求和关系使用中文语义表达**，不用 `Σ`、`∑` 等数学求和符号。例如：`正向修正总和 = 所有正向修正值之和`。
- 用等号表达的计算关系写成 `名称 = 表达式`，等号两侧保留一个空格；条件映射用 `结果 = 条件` 的顺序，多个条件分别成行。
- 语法高亮只是辅助——即使编辑器不显示颜色，代码块内容也必须能独立读懂；不要为了高亮的颜色效果把普通策划正文整体塞进代码块。
- 代码块可能被误认为正式配置或实际代码时，用一句话说明其性质和用途；标题或前文已说明用途时不再重复解释。
- 程序实现参考一律使用项目实际采用的 Godot C#，不换其他语言。

### 4.6 数据规则：区分存储与计算

涉及存档或配置时，只罗列字段名不够，还要说明字段为什么存在、从哪里获得，分成两类：

- **需要存储**：写清字段名、归属对象、写入时机和用途。
- **读取配置或计算获得**：写清结果名、数据来源、计算依据和刷新时机。

示例（数据结构表，允许保留表格形式）：

```markdown
| 字段 | 类型 | 归属 | 写入时机 | 用途 |
|------|------|------|----------|------|
| 佣兵 ID | `string` | 玩家存档 | 招募成功时 | 索引该佣兵的持久化数据 |

| 计算结果 | 类型 | 数据来源 | 计算规则 | 刷新时机 |
|----------|------|----------|----------|----------|
| 品质 | `int` | 成长率档次表 | 按成长率区间映射 | 打开界面或成长率变化时 |
```

- 不要把"存储字段"和"显示字段"混为一谈。
- 能由稳定数据计算出的结果，默认不重复存储；确需缓存时说明原因和失效条件。
- 暂无依赖文档时省略对应依赖项，禁止填写占位引用。

**配置表格式：**

- 每列代表一个配置字段时，表头分隔线下第一行填写各字段的实际存储类型，并统一写成加粗行内代码；类型行不属于配置数据。一行代表一个字段的字段清单不增加类型行，改用独立的“类型”列。
- 类型按实际存储方式填写。只有两个稳定互斥状态时使用 `bool`；多个互斥选项存为数字时使用 `int`，并在表格下方写明固定的数字映射。数字映射投入使用后不得重新排序；新增选项使用未占用的数值。程序转换得到的 C# 枚举不写成配置存储类型。
- 字段存在已确认的统一默认值时，在表格下方集中说明；不在每行重复，也不补充未经确认的默认值。
- 字段顺序默认采用“唯一 ID → 资源或绑定对象 → 分类 → 触发条件 → 行为参数”。资源主表以唯一 ID 为第一列，其他表通过该 ID 引用资源，不重复配置资源路径和资源自身属性。
- 字段结构、加载方式和维护方式基本相同的数据优先合并为一张表，并用类型字段区分。只有字段结构、数据来源、维护归属或生命周期明显不同，或者合并会产生大量空字段时才拆表。
- 数量上限、优先级、互斥方式等限制字段，只在当前版本确实使用且取值已经确认时添加，不为假设的未来需求预留。

示例：

```markdown
| 功能 ID【functionId】 | 是否循环【isLoop】 | 绑定类型【bindingType】 |
|-----------------------|---------------------|--------------------------|
| **`string`** | **`bool`** | **`int`** |
| function_01 | `false` | `1` |

绑定类型：`1` = 界面，`2` = 战斗流程。
默认数据：是否循环为 `false`。
```

### 4.7 排序与默认状态必须可执行

排序规则要写成明确的优先级链，避免"优先显示更好的角色"这类无法实现和验收的描述：

```markdown
排序优先级从高到低：

1. 当前队伍成员优先。
2. 成长率降序。
3. 等级降序。
4. 名称升序，作为稳定的最终排序条件。
```

- 必须写清升序或降序。
- 必须提供稳定的最终排序条件；除非设计明确要求每次刷新变化，否则不要用"随机排列"处理同值项。
- 默认页签、默认选中对象、空列表、无可选对象和超出显示数量等状态，只有当前功能确实可能出现，且处理方式无法由通用界面规则直接推出时才说明；不存在或采用唯一默认处理的状态不枚举。

### 4.8 交互流程只写实际决策

先按 [4.2 节](#42-规则界面流程三个切面)确认确实需要流程，再检查以下六项是否存在尚未定义、且通过 [1.2 节](#12-一条铁律)两道门槛的决策：

- **触发**：玩家做了什么？
- **前置条件**：什么情况下允许或禁止？
- **系统动作**：程序按什么顺序处理？
- **界面反馈**：玩家看到什么变化、提示或动画？
- **数据结果**：哪些数据被新增、修改或删除？
- **异常与收尾**：失败、取消、关闭或重复操作时怎么办？

六项只用于发现遗漏，不是输出提纲，不得为了"闭环"逐项生成文字。某项不存在、只有一种合理处理、不会变化或沿用全局规则时省略。流程用有序列表表示时间顺序，同一步内的并列结果才用无序列表。

```markdown
### 3.1 入队

**前置条件**：当前队伍存在空位。

1. 玩家点击未入队佣兵右侧的"入队"按钮。
2. 系统将佣兵 ID 写入当前队伍数据。
3. 上方队伍列表和下方队伍头像同步刷新。
4. 佣兵从未入队列表移除，其余条目按排序规则补位。

**不可操作状态**：队伍已满时按钮置灰，悬停显示提示"当前队伍已满，无法加入"。
```

- 操作同时改变多个独立数据或界面区域，且这些变化不能从操作结果直接推出时，才逐项写明；否则一句结果足够。
- 删除、消耗、覆盖等不可逆操作必须写确认、取消、遮罩或防误触规则。
- 动画只有方向、先后、时长或可配置方式属于本次设计决定时才说明；由动作资源或全局表现规则决定时只引用来源，不枚举动作组成。
- 涉及多处同步显示时，只列出独立数据源或非自动联动的区域；使用同一数据自然刷新的显示不逐项枚举。
- 规则已定义的条件在流程里写"按上述规则校验"，不逐条复述；总体流程已定义的页面跳转，局部流程不再重复。

### 4.9 去重、精简与设计理由

- 同一事实只在负责定义它的章节完整描述一次，其他章节用链接或一句话引用。
- 默认行为不解释；只有项目偏离默认行为，或确有多个合理处理方式时，才记录差异。
- 禁令与边界条件只有在当前版本可触发、存在自然的错误实现路径、默认处理会造成实质后果，且其他规则尚未覆盖时才保留。
- 纯程序技术约束只有存在已确认的架构分歧或实现风险时才记录，并放入程序对接附录，不混入玩法正文。
- 标题已表达对象时，正文直接写规则，不重复介绍对象。
- 列表、表格、公式、图片或代码块能独立表达的信息，不再用自然段复述。
- 举例、枚举组成部分或换角度解释，只有其中每一项都会改变需求时才保留；仅帮助想象但不改变结果时删除。
- 模板中的章节和字段除明确标记必填外均按需使用，无内容时直接省略。

完成一个模块后，逐句或逐块执行反事实删除：

1. 删除后，两名合理读者是否可能得到不同的设计、实现或验收结果？如果不会，删除。
2. 是否能从标题、上下文、图表、配置、全局约定或引用文档直接推出？如果能，删除。
3. 如果是禁令或边界条件，当前版本是否真能触发，是否存在自然的错误路径和实质后果？任一项为否，删除。
4. 是否已在其他位置定义？保留一个锚点；只有不引用会误读时才在其他位置加链接。
5. 删除整个界面、规则或流程切面后信息是否仍然完整？如果完整，删除该切面和空标题。

**设计理由的写法**：规则的"为什么"只在设计不直观、存在重要取舍或容易被错误修改时说明，用 `> **设计说明**：` 引用块单独标记，一两句写清关键取舍即可；更完整的推演放入独立的设计记录并在文档中链接。注意：关键取舍的推理痕迹值得保留，它是文档区别于程序配置、可供复盘的资产——不要为了篇幅把"为什么"整段删除，也不要为了填篇幅给每条规则硬编理由。

### 4.10 共用规则与布局差异分开写

横版、竖版或不同平台功能相同但位置不同时，不要复制整套功能说明：

```markdown
## 1. 共用功能

这里写打开、切换、入队、离队等共同逻辑。

## 2. 布局差异

**竖版：**

- 队伍信息位于上方。
- 队伍信息从上到下入场。

**横版：**

- 队伍信息位于左侧。
- 队伍信息从左到右入场。
```

只在差异章节写位置、尺寸、方向、分页方式等变化。差异点少时按布局分组列表；只有差异项很多、确实需要逐项横向比较时才用对照表。功能规则本身有差异时，链接到独立小节，避免两份近似文本日后互相矛盾。

### 4.11 中文术语、文案与长段

- **中文术语为主，英文只做映射**：标题、正文、公式、流程和图片说明默认只用中文术语。首次需要对应程序变量时写成 `中文名称【英文变量】`，例如 `最终命中率【finalHitChance】`；完成映射后，后续正文和公式只使用中文名称。配置表、数据结构表和接口表等程序直接查阅的位置，名称列同样使用 `中文名称【英文变量】`。`【】`只用于中英文对应关系，不用于普通强调。
- 必须保持实际语法可复制的代码（JSON、YAML、Godot C# 等）可以使用英文变量，但代码块前必须提供中文映射，代码块后的说明继续用中文。
- **界面文案与人话分开**：玩家实际看到的文字（按钮、提示、弹窗文案）用引号标出，与策划说明分开写，例如 `按钮"入队"`。
- **一段只表达一个结论**：出现多个条件、步骤或结果时拆成列表。
- 禁止"本节主要介绍""为了便于理解""简单来说"等无信息过渡句，结论直接写。
- 规则句优先使用"条件 → 行为 → 结果"的顺序。
- 补充背景不插进主流程中间，用 `> **设计说明**：` 引用块。
- 引用其他方案时使用可点击的相对链接（写法见[第 8 节](#8-跨文档引用)）；文档尚不存在时不写引用或占位标记。

## 5. 界面、流程与图示

### 5.1 制图纪律

流程图、示意图和 UI 图统一使用 draw.io 制作：

- 文档位于某个分类目录时，全部图示统一放在该分类目录下的公共 `img/` 目录；Markdown 使用 `img/{文件名}.png` 相对路径。禁止新建 `images/` 或文档专属图片目录。
- 可编辑源文件用 `.drawio` 格式，与导出的 `.png` 放在同一 `img/` 目录、使用相同文件名；中间产物 `.svg` 可选，不能替代 `.drawio` 和 `.png`。
- Markdown 引用导出的 `.png`，不直接引用 `.drawio` 源文件。
- 修改图示时必须先更新 `.drawio` 源文件，再重新导出同名 `.png`；新增图示时两者一起提交。禁止只修改导出图。

### 5.2 图示使用判定

写作前判断图示能否显著降低理解成本。命中下列任一情况时必须制作图示：

- **流程/状态**：存在三个以上状态、步骤或节点，以及转移、分支、循环或优先级关系。
- **空间结构**：存在空间位置、层级、范围、边界、镜头运动、遮挡或区域扩展关系。
- **输入映射**：存在三项以上输入与行为映射，需要快速建立操作全貌。
- **曲线联动**：存在连续数值变化、曲线联动、阈值或上下限关系。
- **结构总览**：同一机制的结构关系分散在多个段落中，读者必须来回对照才能建立整体认识。

单一事实、一步操作或两项直接对照能用文字或表格说清时不制图。每张图只解决一个核心理解问题；图中的术语、数值、状态和流向必须与正文一致，不添加装饰性内容。

### 5.3 流程图怎么画

- 绘图前先判断流程属于线性、分支、循环还是混合结构，不强制所有流程采用单一方向；默认采用**从上到下的竖向主流程**，前置条件、影响因素和补充结果放主流程两侧。画布宽度与高度按内容自然延长，不得为适配固定尺寸压缩节点、间距或连线。
- 只有竖向布局会明显增加交叉、破坏循环结构或降低可读性时，才改用横向或其他布局。
- 分支以主要路径为视觉主干，同一判断节点的并列分支保持对齐；循环围绕清晰的闭合区域排列，中央留空；混合流程先把主流程、主循环和辅助分支分到不同视觉区域。
- 多个同类节点指向同一目标时，先汇入一条公共连接线再接入目标。
- 连线优先用水平、垂直的正交折线；连线不得穿过节点、文字或说明；条件、动作和影响说明放在对应线段附近，不压在交叉点或折角上。
- 主流程用实线；影响关系、数据依赖等非流程关系可以用虚线，但必须在图中说明虚线含义。颜色只辅助区分模块，流程方向、节点类型和关系必须通过位置、形状、文字与线型表达。
- 同类节点保持相同尺寸，同级节点对齐并留足间距。
- 只有确实存在先后或影响关系的节点才允许连接，禁止为版面对称增加无意义线路。
- 布局的验收标准只有一条：**线条少交叉、少折返、方向统一、节点对齐、留白充足，任何人一眼能追踪每条线的起点到终点**。调整布局时搜索全图同类结构统一处理，禁止只修被指出的局部示例。

### 5.4 流程的文字说明

页面跳转、状态转移或条件分支需要文字说明时，用 `text` 代码块写树状说明，供快速阅读和检索；它不是 draw.io 源文件的替代品。

```text
准备战斗界面
├─ 离开 → 大世界界面
└─ 开战 → 战场资源是否就绪？
           ├─ 是 → 战斗界面
           └─ 否 → 战场加载界面 → 战斗界面
```

- 每个主要页面或状态单独成行，名称与正文一致。
- 单一路径用 `→` 串联，按"触发或动作 → 结果页面或状态"书写；同一行可连续串联多个页面。
- 分支用 `├─` 表示后面还有分支、`└─` 表示最后一个；子分支缩进到所属节点下方，同级分支左对齐。
- 条件判断写成明确问题，分支写明条件结果（如"是""否"），禁止"情况一""其他"这类含义不明的写法。
- 文字说明与 draw.io 图的节点名称、分支条件和流向必须一致。
- **总体流程**只定义跨模块、跨页面的主路径和关键分支；**局部流程**只补充模块内部处理，总体流程已定义的跳转不再逐步复述。简单的"点击按钮 → 进入下一界面"只在总体流程或界面表中定义一次。

### 5.5 UI 图与编号对照

界面图回答"在哪里、显示什么"。图片本身无法说明交互入口、显示状态或元素含义时，再用外置编号和编号对照表补充；复杂条件、后台处理和完整流程不写进界面表。

- UI 图按目标界面的实际分辨率制作，当前桌面端使用 1920×1080；该尺寸**只约束 UI 图**，不约束流程图、示意图等按内容延展的图示。
- UI 图必须用闭合边框明确划分屏幕区域，屏幕比例与目标界面一致；界面元素只放在屏幕区域内。
- 有交互需要解释入口或直接结果、无交互但存在多种显示状态时使用引导说明；其他情况下仅当图片无法独立说明元素含义时使用。静态、单一状态且图已表达清楚的内容不加编号。
- 编号对照表只收录需要文字解释的元素，不要求覆盖图中全部元素：

```markdown
![队伍管理界面总览](img/队伍管理界面总览.png)

| 编号 | 名称 | 说明 |
|------|------|------|
| 1 | 队伍信息 | 显示当前队伍的角色与状态 |
| 2 | 入队按钮 | 执行"入队"流程 |
```

- 说明编号**按单张图片独立计算**：每张图从 `1` 开始连续递增，不跨图片延续；编号表只对应紧邻其上方的单张图片。
- 说明编号和说明文字放在屏幕区域外，说明框按目标元素位置就近分散到上、下、左、右的空白处，不默认集中在单侧；同侧多个说明框保持对齐和间距、不重叠。
- 每个编号用引导线指向屏幕区域内的对应元素，引导线不遮挡关键文字和按钮，不与其他引导线重叠、交叉或合流，每条线能从说明框独立追踪到唯一目标。
- "名称"只写控件或区域名；"说明"只写显示内容、可见状态、简单交互结果或指向规则/流程的引用。一行只解释一个编号。单次操作直接产生结果时，可在"说明"里一句话写明，不再单列流程。
- 同一界面在一篇文档中只完整展示和编号一次，复用时链接到首次定义处并只写差异。
- 图片用相对路径，替代文字要能说明内容；禁止只写 `图片1`、`截图`。Word 文档转 Markdown 时图片文字无法辨认的，必须补编号表，不能假设读者能从截图猜出含义。

### 5.6 状态语义不依赖颜色

Word 可以用红字和黄底传递状态，但 Markdown 在不同编辑器中的颜色显示不稳定。状态必须通过文字和固定标记表达，颜色只能作辅助：

- 红色文字表达的变更写进更新记录，正文只保留最终规则，不长期保留"红字版本"。
- 黄色底纹表示内容未确认：迁移前先在对话中确认，获得答复后写入结论；未获得答复则不写入 Markdown。
- 加粗小标题改写为 `**入队流程：**` 或三级标题。
- 方括号补充说明改写为 `> **实现备注**：说明`，用于标记来源、实现边界或多语言字段。
- 禁止只写"红色部分有修改"。Markdown 正文只保留已确认内容。

## 6. 版本、状态与确认流程

### 6.1 版本号规则

版本号由"主版本号.修订序号"组成。**小数点只是分隔符，不是十进制小数**——修订序号达到 9 后继续递增为 10，不得进位主版本号。

- **AI 刚生成**：使用 `v0.1`，表示内容未经人工确认。
- **修订更新**：保持主版本号不变，修订序号加 1，例如 `v0.9 → v0.10`、`v1.9 → v1.10`。
- **主版本变更**（如 `v1.x → v2.x`）：只有策划口头确认后才能修改。AI 不得因"大改""定稿"或修订序号较大而自行进位，也不得把 `v1.9` 写成 `v2.0`。

### 6.2 更新记录保护

更新记录是文档的历史账本，不是当前格式的展示区。AI 修改文档时，默认只能处理自己这次产生的版本记录。

正确做法：

- 本次小改，就追加一行新记录，例如 `v0.3 | 2026-07-06 | Codex+lm | 修正视野机制`。
- 刚追加的本次记录写错了，可以修改这一行。
- 更新说明只写"改了什么"，控制在 30 个汉字以内；写不全就用"..."收尾。不引用"已决策"内容、编号或跳转链接，不新增单独的"更新说明"章节复述记录。

错误做法：

- 把历史记录里的 `Claude` 批量改成 `Codex`，或为了统一格式改写旧版本的作者、日期、版本号。
- 顺手合并、删减、重写旧版本的更新说明。
- 发现旧记录可能有误时不指出，直接修改。
- 文档从 `调优中` 改为 `已定稿` 后继续保留 `v0.x` 更新记录（主版本为 0 的记录在定稿时删除；旧行的版本号、日期、作者始终不变）。

> **说明**：策划明确要求格式整理旧更新记录时，只允许把旧行的更新说明压缩到 30 字以内；版本号、日期、作者是历史事实，不能改动。

### 6.3 文档的四种状态

```text
初稿  →  调优中  →  已定稿
                         ↓
                      已废弃
```

- **初稿**：AI 刚完成，内容未经策划整体审核，结构和规则都可调整。
- **调优中**：策划正在修改或验证已有规则；修改时递增修订序号，主版本号仍需策划口头确认。
- **已定稿**：内容已确认，只允许调整数值，不能直接大改结构。
- **已废弃**：已被新版本替代，只保留作历史记录，不再修改。

### 6.4 未确认内容与提问规则

策划文档只记录已确定且需要执行的内容。AI 生成或修改文档时，发现关键数值、方案选择、规则归属或缺失内容无法自行确定，**必须在对话中直接提问，不能把问题写进文档**。

1. AI 在写入前提出具体问题，并说明该问题影响的规则。
2. 用户回答后，AI 只把确认后的结论写入对应章节。
3. 用户未回答时省略该内容；不得写入暂定值、候选方案、占位符或待办标记。
4. 缺少答案会导致整篇文档无法成立时，停止生成并说明阻塞原因，不提交含猜测内容的文档。

禁止写入文档的内容：

- `待确认`、`待定`、`待补充`、`TODO` 等未完成标记。
- 未经确认的临时数值、推荐数值或 A/B 候选方案。
- "当前先这样""后续再调整""建议以后加入"等未形成执行结论的内容。
- 独立的"待确认项""待调优清单"或同类章节。
- 不设置独立的"验收标准"模块：可验证条件与预期结果写入对应功能、流程或边界条件。
- 不列举"不负责""不处理""不支持"或未计划实现的功能；正文未定义即不在实施范围。
- 不写仅用于阻止反常实现、无现实发生路径或当前版本无法触发的问题；技术上可以想象不等于值得记录。
- 不把唯一合理的默认行为改写成禁令、边界条件或实现说明。
- 不为满足流程检查、边界条件、模板章节或 `ai_context` 检查项而补写没有独立决策的信息。
- 不为文档擅自发明规范未定义的 YAML 字段、切面或章节。

需要 playtest 的已确认规则可以写入验证方案，但正文必须使用当前确定的执行值，不能以"待测试"代替规则。

## 8. 跨文档引用

游戏系统之间不是孤立的，设计文档之间也有依赖关系。引用其他系统时必须写**可点击的相对路径**，让 AI 和人能找到；只写文档名或绝对路径都无法定位。

正确写法：

```markdown
✅ [势头系统](lm_势头系统20260706.md)
✅ [属性体系](../战斗/lm_属性体系20260701.md)   ← 用相对路径
```

错误写法：

```markdown
❌ 参考命中系统文档              ← 没有文件名，找不到
❌ D:/策划/战斗/属性体系.md      ← 绝对路径，换台电脑就失效
```

引用不能替代当前文档必须执行的结论。当前功能所需规则能用一两句话说清时，先在本文写明条件与结果，再链接到来源文档中的详细计算或完整定义；不得只写“按某文档执行”，使读者必须跳转后才知道当前功能要做什么。来源文档已经完整定义的公式、数值表或处理流程不在本文重复。

```markdown
✅ 声源未进入听力范围时不播放声音；听力值的计算见[视野声音表现](../战斗/视野声音表现.md)。
❌ 视野外声音按[视野声音表现](../战斗/视野声音表现.md)执行。
```

引用游戏以外的资料（Wiki、官方文档等）直接写完整链接：

```markdown
参考：[Battle Brothers Wiki](https://battlebrothers.fandom.com)
参考：[Godot 4.x C# API](https://docs.godotengine.org/en/stable/classes/)
```

## 附录 A：AI 执行细则

> 本附录是 AI 生成与修改策划文档时的执行细则，也是人审稿时的对照表。
> 策划日常写文档不必通读本附录；规则定义以正文为准，本附录只提供执行细节、
> 格式速查和检查单，不重复正文规则。正文与附录冲突时，以正文为准并报告差异。

### A.1 语言标记与键值格式速查

正文 [4.5 节](#45-公式与代码块写法)的原则在此给出可执行格式：

| 内容类型 | 语言标记 | 格式要点 |
|----------|----------|----------|
| Markdown 写法示例 | `markdown` | 展示章节结构、正文写法 |
| Godot C# 实现参考 | `csharp` | 项目实际采用的 Godot 4 C# |
| JSON 数据 | `json` | 保持可复制语法 |
| YAML 头部、配置或键值型规则 | `yaml` | 键值型规则保持 YAML 可识别的 `名称: 内容` 结构；该代码块不因此视为程序配置 |
| 计算关系或条件映射 | `ini` | 计算用 `名称 = 表达式`，等号两侧各留一个空格；条件映射用 `结果 = 条件`，多个条件分别成行 |
| 树状流程说明或纯文本结构 | `text` | 见正文 [5.4 节](#54-流程的文字说明) |

- 代码块必须填写正确的语言标记以启用语法高亮。
- 不符合键值结构的伪代码、纯文本一律用 `text`，不冒充其他语言。
- 高亮只是辅助：即使不显示颜色，代码块内容也必须能独立读懂。

### A.2 公式中的中文语义

- 求和关系使用中文语义表达，不使用 `Σ`、`∑` 等数学求和符号：`优势修正总和 = 所有单个优势源修正值之和`。
- 公式变量与程序变量的映射见正文 [4.11 节](#411-中文术语文案与长段)。

### A.3 ai_context 怎么写

`ai_context` 用于声明生成约束、参考文档、必须检查的内容和风格要求。建议包含：

- **生成约束**：哪些旧规则作废、本次必须遵守的硬性限制，例如"势头战斗内锁定，不增不减"。
- **参考文档**：写作前必须读取的文档路径列表，例如"参考：策划/战斗/属性体系.md"。
- **必须检查**：生成前必须检查是否存在独立决策的关键主题，例如"必须检查：优劣势源体系、燃烧机制"。检查项不等于输出项；只有通过正文信息准入门槛的结论才写入。
- **风格要求**：表达方式，例如"直接写结论；并列规则用列表；表格只放结构化数据；不复述相邻内容"。

旧文档 `ai_context` 中的"必须覆盖"统一按"必须检查"理解，无需批量迁移，也不得据此为每个主题创建章节或说明。

真实例子：

```yaml
ai_context: |
  本文档定义势头系统的核心逻辑。
  约束：战斗内势头锁定，唯一例外是主动燃烧；
       势头只放大同侧修正（正→优势，负→劣势）；
       灵魂硬币债务独立于势头系统。
  参考：策划/战斗/命中系统.md
  必须检查：优劣势源体系、燃烧机制、灵魂硬币债务
```

新文档不得省略 `ai_context`；内容较多时正文末尾追加"附录：AI 生成说明"展开（见 [7.2 节](#72-system系统设计模板)），YAML 保留摘要。

### A.4 生成与自查总检查单

````markdown
## 1. 概述

> **一句话定位**：势头是团队运势指示器，只放大战场上已有的优劣势，不创造命中。

**核心目标：**让团队运势影响已有战场条件，但不替代站位、属性和战术决策。

> **设计说明**：采用"只放大不创造"而非直接加减命中，是为了让运势成为战局放大器而非独立命中来源，避免它架空站位价值。

---

## 2. 核心公式

```ini
有效命中率 = clamp(基础命中 + 优势修正总和 - 劣势修正总和, 5%, 95%)

单个优势源修正值 = 5% + 势头对优势源的放大值
优势修正总和 = 所有单个优势源修正值之和

单个劣势源修正值 = 5% + 势头对劣势源的放大值
劣势修正总和 = 所有单个劣势源修正值之和

[势头放大规则]
势头 > 0 = 优势源额外 +|势头|%，劣势源不变
势头 < 0 = 劣势源额外 +|势头|%，优势源不变
```

---

## 3. 功能与规则

### 3.1 战斗内锁定

- 势头进入战斗后保持不变，主动燃烧除外。

### 3.2 燃烧与债务

- 正燃烧：每人独立概率 = 燃烧时势头 × 10%，获得 +1 行动点。
- 负燃烧：势头归零，欠 |势头| 枚灵魂硬币债务。
- 欠债期间势头锁死为 0，所有增减事件不生效。

### 3.3 优劣势源数量

- 优劣势源没有硬上限，实际数量由战场站位可形成的来源决定。

---

## 4. 数据规则

| 参数 | 值 | 说明 |
|------|----|------|
| 最小值 | -6 | 下限封顶 |
| 最大值 | +10 | 上限封顶 |
| 自然趋中 | 1 点 / 7 天 | 结算时机：每日刷新 |
| 正燃烧条件 | ≥ +3 | 满足时结算正燃烧 |
| 负燃烧条件 | ≤ -1 | 满足时结算负燃烧 |
````

示例要点回顾：概述有定位、目标与一处设计说明；公式用中文语义求和；功能模块标题具体、规则正文直接跟在标题下；数据规则表集中记录数值与结算时机。"势头锁死时不能正燃"可由锁死值与正燃门槛直接推出，因此不写成边界条件；优劣势源无硬上限属于独立决策，写在负责它的功能模块中。本示例未含界面、流程与独立边界章节——它们没有新增信息，按 [1.2 节](#12-一条铁律)与 [4.2 节](#42-规则界面流程三个切面)省略。

## 附录 C：专业名词说明

专业名词同样以中文名称为主、英文名称作映射。首次出现或接口需要时写成 `中文名称【英文名称】`，后续统一使用中文名称。

- 提示【tips】：用于显示对象补充或详细信息的浮窗界面。
- 增益【buff】：正向状态效果。
- 减益【debuff】：负向状态效果。
- 冷却时间【CD / cooldown】：技能再次可用前需要等待的时间。
- 持续伤害【DOT / Damage Over Time】：在一段时间内多次结算的伤害。
- 范围效果【AOE / Area of Effect】：同时影响一定区域内目标的效果。
- 每秒伤害【DPS / Damage Per Second】：单位时间内造成的平均伤害。
- 非玩家角色【NPC / Non-Player Character】：不由玩家直接控制的角色。
- 战斗界面【HUD / Heads-Up Display】：战斗画面上持续显示的信息区域。
- 行动点【AP / Action Point】：单位执行战斗行动消耗的资源。

此列表持续维护。新增专业名词时先确定中文名称，再补充英文名称映射。
