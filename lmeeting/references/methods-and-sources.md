# 方法依据与适用边界

网页核查日期：2026-09-16。以下依据来自实际读取的原始方法页面；它们是实践框架，不用于声称本技能已被实验证明优于所有会议方法。

## 用户提供的核心流程

本技能的主体来自用户提出的美术会议方法：

1. 从 N 个参考游戏中先排除技术不可实现项。
2. 再检查平台适配、游戏设定和其他能排除一类方案的共性规则。
3. 想不到其他客观因素时，让每个人提出希望排除的内容，从理由中寻找可验证的客观原因，再针对原因讨论解决方法；主观排除用于发现问题，不直接决定淘汰。
4. 最终选择保底最低水平、努力追赶目标、平级局部参考各一个。
5. 形成风格决定，进入实际制作。

这套顺序及三个参考角色不是下述网页提出的模型，不能归功于外部方法。

用户进一步明确的核心是“先用客观因素排除不合适项，再从主观排除理由中寻找客观原因及其解决方法”。本技能据此区分可解决问题与实际淘汰条件；解决方法尚未验证时仍记为待验证。

用户随后要求扩展到游戏项目的其他会议。通用技能按探索、决策、协调、验收与复盘区分目的，原美术筛选顺序和三个参考作为专用流程保留；不将该数量或排除步骤强加到其他会议。

用户进一步补充：不同人对同一名词及程度可能理解不同，应先用具体图片和游戏案例对齐认知，再用具体游戏及其明确维度描述目标。技能据此加入共同锚点、维度拆分、复述确认和来源记录；这些要求来自用户的项目实践，不归因于下述外部方法。

## 1. DACI：让决策权与执行责任明确

- 来源：[Atlassian Team Playbook — DACI Decision-Making Framework](https://www.atlassian.com/team-playbook/plays/daci)
- 原文方法：明确 Driver（推进人）、Approver（一名最终决策人）、Contributors（提供专业意见的人）、Informed（需知会结果的人）；整理背景、决策因素、候选方案和所需信息，安排行动项并记录结果。
- 本技能采用：会前确认推进人与决策人；会末记录选择理由、行动负责人和交付要求。
- 适用边界：这是明确分工的建议，不表示管理者可以投票改变技术事实。沿用团队已有授权；不要为套用缩写新增不必要的职位或审批。
- 原网页提到分享结果；本技能仅要求形成可分享的记录，实际通知仍取决于本次用户授权。

## 2. 1-2-4-All：先独立思考，再扩大讨论

- 来源：[Liberating Structures — 1-2-4-All](https://www.liberatingstructures.com/1-2-4-all)
- 方法开发者：Henri Lipmanowicz、Keith McCandless。
- 原文方法：个人安静思考并记录，再两人交流、四人归纳，最后全体分享。强调让每个人参与、延后评判、主持人不过度控制。当前页面给出约 15 分钟的流程示例。
- 本技能采用：大家先各自写排除意见，再分享和澄清，从中发现遗漏的客观问题，并共同寻找解决方法；人数较多时采用分组递进。小团队可直接轮流发言。
- 适用边界：这里将参与结构用于收集筛选意见，不宣称原方法专为“排除”设计。原方法的完整分组至少需要四人；本技能中的短时间静默书写和轮流分享是简化调整，不应称为完整执行了 1-2-4-All。

## 3. Scrum Guide：按会议目的区分计划、协调、评审与改进

- 来源：[The Scrum Guide（2020）](https://scrumguides.org/scrum-guide.html)，Ken Schwaber、Jeff Sutherland；本次扩展实际读取。
- 原文方法：计划讨论为什么有价值、能完成什么、如何完成；日常协调检查目标进展并调整行动；评审检查实际成果并讨论后续调整；回顾寻找提高质量与效率的改进。完成定义让参与者对已完成工作有共同理解，执行工作的人负责估算。
- 本技能采用：会议按目的组织；排期检查实际能力和完成条件；协调聚焦阻塞；验收看实际成果；复盘落实最有用的改进。
- 适用边界：只借用这些原则，不要求游戏团队采用 Sprint、特定职位、固定频率或整套 Scrum。技能中的会议时长和游戏场景不冒充原文规定；不把阶段验收当成 Scrum 原文要求的发布审批。

## 4. Google SRE：复盘还原原因并落实预防行动

- 来源：[Postmortem Culture: Learning from Failure](https://sre.google/sre-book/postmortem-culture/)，Google SRE 第 15 章；本次扩展实际读取。
- 原文方法：记录事件、影响、缓解或解决动作、原因及后续行动。无责复盘考察当时信息和系统性条件，避免责难使问题被隐藏；复盘要审阅并形成可执行的改善。
- 本技能采用：返工、延期、线上事故和协作失误复盘先还原事实，分析多个可能的促成因素，检查后续改进效果，避免止于“某人不认真”。
- 适用边界：原文面向可靠性事故，此处向游戏制作复盘作有边界的迁移，不声称它验证了游戏会议效果。明确动作和改进负责人仍有必要；原文中的传播流程不授权自动发送会议记录。

## 本技能的综合设计

以下是面向本次需求补充的操作规则，不冒充网页原话或经过量化验证的结论：

- 将硬约束、待验证预测与个人偏好分开，避免用投票判断可实现性。
- 主观意见只是问题线索；先核实原因、讨论解决方法，再按结果保留、调整、验证或排除，不能把偏好包装成客观理由。
- 对整款游戏与可参考局部分别判断；同一规则一致应用于所有同类候选。
- 筛掉不合格项后，转为正向比较，不无限寻找淘汰理由。
- 三个参考必须落实为一个风格定义；借鉴部分要相容，不能拼成三套风格。
- 用实际小样验证视觉、性能与持续制作成本，预先约定失败后的调整范围。
- 限时议程、另议清单和会末回读是可调整的主持措施。模板中的 75 分钟安排仅是起点。
- 先写后说、决策者晚表态、具体情境走查、假想失败、最小验证、依赖交接、按新证据重开决定等是本技能组合的主持建议，不将全部做法归于某一个来源。
- 试玩中区分观察、原话、原因假设和建议；玩法、数值、叙事与 UI 等场景的流程是游戏项目适配建议。玩家主观体验的价值与原因是否已被证实分开处理，不声称量化指标可以穷尽乐趣。
