# 第 3 章：坐标空间

### 第 3 章：坐标空间 —— 从模型到屏幕的旅程
**学习目标**：理解 3D 顶点从"物体自我坐标"到"屏幕像素"经历的六层坐标空间，重点吃透裁剪空间 → NDC → 屏幕空间这段最绕的链路；理解 2D 是 3D 管线在正交投影下的退化特例。

**场景搭建**：本章是概念章，建议两套场景对照运行——3D 用 MeshInstance3D + Camera3D + DirectionalLight3D；2D 用 Sprite2D 挂 shader_type canvas_item 的 shader。最后一节的可视化练习只需要 2D 场景。

**内容要点**：
- 图形学认知基石：为什么渲染管线需要这么多层坐标空间
- 3D 空间链：Model → World → View → Clip → NDC → Screen（六层）
- 模型 / 世界 / 视图三层空间：相对好理解，靠矩阵搬运
- 裁剪空间：为什么需要它、和 NDC 是什么关系、最后如何到屏幕
- 透视除法和 w 分量：为什么 NDC 阶段要 ÷w
- 视锥体、近平面 / 远平面 / FOV：ch21/22 重建深度时用到的概念
- 非线性深度：为什么深度缓冲要这样设计、为什么需要"线性化"
- 2D 是 3D 的特例：为什么 Godot 中 2D 也用 mat4
- 可视化练习：坐标就是颜色

## 3.1 为什么需要这么多坐标空间
在动手 shader 之前，先把一个概念钉牢：**同一个顶点，在不同语境下有不同的"身份"**。

想象你站在房间里。问你"在哪里"，可能有三种回答：

- **对自己说**："我在我的两只脚的正上方 1.7 米处"——相对于自身的坐标。
- **对房主说**："我在房间门口往北 2 米"——相对于房间的坐标。
- **对地图说**："北纬 30°，东经 120°，海拔 20 米"——相对于地球的坐标。
同一个你，同一个位置，三种表述。**哪种对取决于"谁在问"**。GPU 面临同样的问题：一个三角形的顶点带着"出生坐标"（相对于模型中心）来到 shader，但要经过多次"翻译"才能变成屏幕上的像素。每次翻译，输入坐标属于一个空间，输出的是另一个空间的坐标。

### 3.1.1 为什么不能一步到位？
理论上，你完全可以写一个矩阵 M_final，把模型坐标直接变成屏幕像素：pixel = M_final * vertex。为什么 GPU 要拆成五六步？

三个工程原因：

- **可组合性**：管线中每一步都可能要被独立修改。你想"只移动物体、不动摄像机"，就改 MODEL_MATRIX；"只动摄像机、移物体不动"，就改 VIEW_MATRIX。如果只有一个大矩阵，任何小变化都得重算整体。
- **裁剪效率**：GPU 要在三角形离开屏幕前丢弃它。这件事在"裁剪空间"里最便宜——只要检查 |x'|, |y'|, |z'| 是否都小于 |w'| 即可（等价于后续 ÷w 之后是否落在 [-1, 1]³ 立方体内）。如果在世界空间做，得为每个图元算复杂的视锥包含。
- **插值正确性**：varying 变量在 vertex→fragment 之间要按透视正确的权重插值，这需要 w 分量——它只有在经过投影矩阵、进入裁剪空间之后才出现。

### 3.1.2 矩阵是什么？
第二章讲过：**矩阵是空间之间的搬运工**。一个 4×4 矩阵 M 一次性编码了"旋转 + 缩放 + 平移"的组合变换，M * vec4(p, 1.0) 把点 p 从源空间搬到目标空间。Godot 把搬运工直接暴露给你，作为 shader 的内置变量，命名规则一致：

X_MATRIX 把一个坐标从某个空间搬到另一个空间。带 INV_ 前缀的是逆矩阵——反向搬运。

关键不是背名字，而是理解**空间链的顺序**——搞清楚从头到尾经过几层。下面按 3D 六层链路依次走一遍。

### 3.1.3 渲染管线与坐标空间的关系
第一章 已讲过渲染管线的六个步骤（顶点输入 → vertex → 图元装配 → 光栅化 → fragment → 帧缓冲）。本章关心的是其中前两步在数学上发生什么：

| 管线阶段 | 坐标空间 | 做的事 |
| vertex() 输入 | 模型空间 | 拿到原始 VERTEX，相对物体自身 |
| vertex() 输出 | 裁剪空间 | 写出 POSITION，准备被 GPU 处理 |
| 图元装配 + 裁剪 | 裁剪空间 → NDC | GPU 自动做透视除法和裁剪 |
| 光栅化 | NDC → 屏幕空间 | GPU 自动视口变换 |
| fragment() 输入 | 屏幕空间 | FRAGCOORD / SCREEN_UV / 插值后的 UV |

后面六节就是这套管线在每一层空间里发生的事。

## 3.2 3D 空间链总览
3D 顶点要走过六层空间，靠五个矩阵搬运（最后一步是 GPU 自动）：

```
模型空间 (Model)
    │  MODEL_MATRIX
    ▼
世界空间 (World)
    │  VIEW_MATRIX
    ▼
视图空间 (View)        ← 摄像机说了算
    │  PROJECTION_MATRIX
    ▼
裁剪空间 (Clip)        ← 齐次坐标 + w
    │  GPU 自动透视除法 (÷ w)
    ▼
NDC (Normalized Device Coordinates)
    │  GPU 自动视口变换
    ▼
屏幕空间 (Screen)      → FRAGCOORD
```
前三层（Model / World / View）相对好理解——就是"用矩阵搬运坐标"，没有任何数学魔法。真正绕的是后三层（Clip / NDC / Screen），它们用齐次坐标的 w 分量编织出"近大远小"。

## 3.3 模型空间 → 世界空间

### 3.3.1 模型空间（Model Space）：顶点的自我身份
这是顶点最原始的状态。VERTEX 在 3D 中是 vec3，值是相对于**模型自身原点**的坐标。

对于一个 1×1 的 PlaneMesh，四个顶点的 VERTEX 大致是 (-0.5, 0.0, -0.5)、(0.5, 0.0, -0.5)、(0.5, 0.0, 0.5)、(-0.5, 0.0, 0.5)。无论你在场景里把这个 MeshInstance3D 放到哪个位置、转成什么角度、放得多大，这些数字永远不变——它们是"模型自己看自己"的视角。

**为什么需要它？** 模型空间是唯一不随节点移动 / 旋转 / 缩放而变化的空间。当你做"相对于物体自身"的效果——让旗帜沿旗杆方向飘、让法线贴图按表面方向扰动——你需要的是局部的、稳定的坐标。**修改 VERTEX 永远在模型空间生效**。

### 3.3.2 世界空间（World Space）：场景共享的坐标
MODEL_MATRIX 负责第一级变换：把顶点从**模型坐标**搬到**世界坐标**。

世界空间是你在 Godot 编辑器 3D 视图中看到的坐标——所有物体共享同一套坐标系，原点是场景根的位置。

```
vec4 world_pos = MODEL_MATRIX * vec4(VERTEX, 1.0);
```

- 你在编辑器里拖动节点（改 position / rotation / scale），引擎就**自动重算它的 MODEL_MATRIX**——节点位置变了，矩阵跟着变。
- MODEL_MATRIX 是 mat4——4×4 齐次矩阵，才能在一次乘法里同时编码旋转 + 缩放 + 平移（ch2 讲过齐次坐标的来历）。
**逆矩阵 INV_MODEL_MATRIX** 做反向搬运：把世界坐标变回模型坐标。当你有世界空间的光源位置，想算"光在模型的哪个方向"时，就用它。

**世界空间解的问题**：当你想判断"物体 A 在物体 B 的左边还是右边"时，需要两者的世界坐标——模型坐标做不了这个判断，因为 A 的模型坐标和 B 的模型坐标互不认识。

---

## 3.4 视图空间
VIEW_MATRIX 把世界坐标变成**从摄像机看过去的坐标**，这就是视图空间（View Space）。逆矩阵 INV_VIEW_MATRIX*能把视图坐标推回世界坐标。

在视图空间中：

- **摄像机永远在原点 (0, 0, 0)**，"看"向 -Z 方向。
- 物体离摄像机越远，Z 值越负（即 Z 的绝对值越大）。
- 这个空间是算**深度**和 **Fresnel 效应**的最佳场所——"物体表面和视线之间的夹角"在视图空间里最直观。
**为什么需要一个独立的视图空间？** 摄像机自己也是场景中的一个物体，它在世界空间里有自己的位置和朝向。如果直接在世界空间做投影计算，每个物体的深度都要拿"物体 - 摄像机"的差算一遍。先把整个世界搬到"以相机为原点"的视图空间，后续所有投影计算都和相机位置脱钩——这是一次性的预处理，让投影矩阵变得简单。

---

## 3.5 视图空间 → 裁剪空间
接下来三节（裁剪空间 → NDC → 屏幕）是整章最关键的部分。先把裁剪空间单独讲透，再讲 NDC 和屏幕。

### 3.5.1 视锥体：相机能看到的有限区域
在视图空间里，相机能看到的范围并不是"无限延伸的锥体"——它被六个平面切出来一个有限的"截头金字塔"：

[IMAGE: 透视](../ch03-diagrams/perstective.webp)  

上图左侧就是透视投影，近平面小而远平面大，右侧是正交投影，两个平面一样大。

透视投影的视锥体有六个平面，分别是：

- **近平面（near plane）**：相机正前方 z = -near 处的平面。比这个还近的物体不会被渲染（贴到相机镜头里的帽子看不见）。
- **远平面（far plane）**：相机正前方 z = -far 处的平面。比这个还远的物体也不渲染（远处的小山可以省掉）。
- 上下左右四个侧面：由相机的 **FOV（Field of View，视场角）** 和长宽比决定。FOV 越大侧面越张开（广角镜头），FOV 越小越窄（长焦镜头）。
Godot 的 Camera3D 暴露这三个参数：near、far、fov。它们定义了一个**有限可见区域**——只有落到视锥体内部的物体才会被渲染。

### 3.5.2 透视投影的几何直觉：先把视锥体"挤"成长方体
要通过透视投影把视锥体这个金字塔直接画到 2D 屏幕上很麻烦：近处的物体大、远处的物体小，是非线性的"近大远小"关系。图形学的经典思路是把这个过程拆成几步，用一段立体几何的直觉来理解：

**第一步：把视锥体"挤压"成一个长方体。** 想象给远平面施加一种"挤压操作"——远平面被逐步压小，尺寸接近平面、最后变得和近平面一样大。挤完之后，原本金字塔形状的视锥体变成了一个规则的长方体（前后一样宽），里面的物体也被一起压扁了：远处的物体向中心收缩、近处的物体保留原比例——这正是"近大远小"的视觉效果。

注意两件事：

- **挤压操作改写的是 x/y**：原本远处的 x/y 因为视锥体更宽所以数值更大，挤压把它压向中心——这就把"近大远小"的视觉效果提前具象了一次。
- **z 在挤压过程中是被保留下来的**：投影矩阵会改写 z 写进 z'，但不会丢弃深度信息——"谁在前、谁在后"并没有丢失。
**第二步：用 w 分量记下"要除的东西"**

为什么要这么绕一下？因为"近大远小"的完整效果其实要 ÷ z 这种非线性除法才会真正显形——而矩阵乘法是线性的，做不了除法。所以投影矩阵不能一步到位把近大远小算出来，它的策略是：

- 用线性变换把视锥体挤压 + 平移缩放到接近标准立方体形状（第一步）；
- 在 w' 里记下"待会儿要除以什么"——也就是 -z；
- 让 GPU 后续做 ÷ w' 这一步（透视除法），这才把近大远小的视觉效果真正"压实"。
w' 在这个策略里扮演的角色是 "延迟做除法的备忘录"。

**第三步：把长方体平移缩放成标准立方体。** 挤压完的长方体还不是标准形状——它的边长由 near/far、FOV、aspect 决定，每台相机都不一样。再用一次线性变换把这个长方体平移、缩放到一个所有相机都一样的标准立方体 [-1, 1]³——这就是 NDC。这一步纯粹是线性变换（平移 + 缩放），没有难点。

**一句话**：透视投影 = "挤压 + 平移缩放"（线性，矩阵做）+ "÷w"（非线性，GPU 硬件做）。PROJECTION_MATRIX 把前两步合成一个矩阵写给你，并把要除的 -z 暂存进 w'，等 GPU 后续 ÷w 时用。理解时拆成这三步看最清楚。

### 3.5.3 PROJECTION_MATRIX 是怎么实现这种挤压的
回到 PROJECTION_MATRIX 把视图空间 (x, y, z) 变成裁剪空间 (x', y', z', w') 的公式：

```
x' =  x · (cot(fov/2) / aspect)
y' =  y ·  cot(fov/2)
z' =  z · (far + near) / (far - near)  +  常数
w' = -z        ← 关键变化
```
为什么 w' = -z 视图空间？因为 z 在视图空间里就是"这个顶点离相机多远"，-z 是因为视图空间看向 -Z 方向，相机前方的物体 z 是负数，加个负号变正、用着方便。这一行就是上一节说的"把深度记进 w"——挤压操作中保留前后关系的关键。

x' 和 y'*是位置分量的"分子"。cot(fov/2)/aspect 和 cot(fov/2) 是按 FOV 和长宽比做的预缩放——这一步把视图空间的水平/竖直坐标按视锥体锥角的形状"压"了一下：远处的 x 算下来比近处的大（远处视锥体更宽），但下一步除以 w'（也大）就会把它压回中心。所以 x'/w' 的最终效果就是"远处的物体 x 在屏幕上更靠中心"——近大远小。

**z'** 是深度分量的"分子"。投影矩阵把视图空间的线性深度 [-near, -far] 加权成 z'，再 ÷w' 得到 NDC 的深度（直接写入深度缓冲）。注意这里的加权 系数 = (far+near)/(far-near) 不是均匀的——近处精度高、远处精度低（3.6.3 节展开）。

### 3.5.4 正交投影 vs 透视投影：w 是关键
Godot Camera3D 支持两类投影。区别体现在 PROJECTION_MATRIX 的 w 处理：

| 类型 | w' 的值 | 效果 | 适用 |
| 透视投影（默认） | w' = -z 视图空间 | 近大远小，平行线汇聚 | 3D 游戏真实视角 |
| 正交投影 | w' = 1.0（恒为 1） | 无近大远小，物体大小恒定 | 2.5D、策略游戏、编辑器视图 |

正交投影下 w' 恒为 1，透视除法 ÷w 等于除以 1，没有变化——所以物体无论远近，屏幕上的大小不变。这正是稍后讲 2D 时会遇到的情形：2D 的投影本质就是正交投影。

## 3.6 裁剪空间 → NDC → 屏幕空间

### 3.6.1 透视除法
把上面的过程串起来：裁剪空间 = 挤压后、但还没 ÷w 的中间状态。NDC 的坐标是把裁剪空间坐标除以 w' 得到的：

```
NDC = (x'/w', y'/w', z'/w')
```
为什么不在投影矩阵里直接做 ÷w、得到 NDC 一次性返回，而要在中间停一停？因为 GPU 在 ÷w 之前要先做裁剪：

- 一个三角形跨越视锥体边界时（一半在内、一半在外），GPU 需要沿边界切开三角形，保留可见部分、丢弃不可见部分。
- 切三角形必须在挤压前的等比线性空间里做，否则切完之后远处被放大的部分和近处被放大的部分尺度不一致，几何关系会失真。
- 在裁剪空间里，还未 ÷w，几何关系还保持着挤压前的等比。
那在裁剪空间里怎么判断"一个顶点挤压后会不会在 NDC 立方体内"？GPU 用一个等价的、不需要做除法的判据：

```
-w' ≤ x' ≤ w'   ⟺   -1 ≤ x'/w' ≤ 1   ⟺   NDC.x ∈ [-1, 1]
```
-w' ≤ 坐标 ≤ w' 只做加减比较，不用做除法——正合 GPU 的胃口。三轴分别套用：

- -w' ≤ x' ≤ w' ⟺ NDC.x ∈ [-1, 1]
- -w' ≤ y' ≤ w' ⟺ NDC.y ∈ [-1, 1]
- -w' ≤ z' ≤ w' ⟺ NDC.z ∈ [-1, 1] 
任何一项不满足就丢弃顶点。部分跨越边界的三角形沿边界切开——这就是 "裁剪" 这个名字的由来：在 ÷w 前用等价判据做的几何裁剪。

**用一句话总结**：投影矩阵把视锥体"挤压"到裁剪空间（保留 w 用作深度账本）；GPU 在 ÷w 之前用 -w' ≤ 坐标 ≤ w' 做等价裁剪；裁剪通过后执行 ÷w，得到真正的 NDC（标准立方体 [-1, 1]³）。裁剪空间和 NDC 的关系就这一条公式：NDC = 裁剪空间 ÷ w'。

### 3.6.2 NDC 的 z 是非线性的
一个容易被忽略的事实：NDC 的 z 分量（就是深度缓冲里存的值）按 1/z 分布，不是线性的。

意思是：近平面到远平面之间的真实距离被压缩成 [0, 1]（Forward+），但这个压缩不是均匀的——近处的 0.1 占了 [0, 0.5] 这么大的范围，远处的 100 米可能挤在 [0.99, 1.0] 一小段里。

**为什么这样设计？** 真实世界近处的细节需要更高的深度分辨力——避免两个相邻表面产生 Z-fighting（深度值过于接近导致的闪烁）。远处因为透视收缩已经很小，深度精度差一点也看不出来。这是渲染管线的"有意偏科"。

**对 shader 工程的影响**：你不能直接拿深度缓冲的原始值做距离比较——近处过度敏感、远处完全失灵。要先把非线性深度反算回视图空间的真实距离。线性化的数学本质就是 3.5 节讲过的"逆投影"：用 INV_PROJECTION_MATRIX 把 NDC 反推回视图空间。这点在 3.8 节展开。

### 3.6.3 NDC → 屏幕空间
NDC 到屏幕像素不是一步完成的，而是**视口变换**——GPU 内部固定硬件自动完成。完整步骤：

- GPU 执行透视除法，得到 NDC
- 视口变换：把 NDC 的 [-1, 1]³ 映射到实际屏幕分辨率
- x：[-1, 1] → [0, viewport_width]
- y：[-1, 1] → [0, viewport_height]，注意 GPU 内部翻转 Y 轴（NDC 中 Y 向上，屏幕坐标系中 Y 向下）
- z：保持 [0, 1] 范围，写入深度缓冲（Forward+/Mobile）
- 光栅化器用视口变换后的坐标判断哪些像素被三角形覆盖
- 被覆盖的像素坐标就是 FRAGCOORD.xy
**你不需要手动做这步**。在 fragment() 里拿到的 FRAGCOORD 已经经过了三步（透视除法 → 视口变换 → 光栅化），FRAGCOORD.xy 是像素坐标（像素中心为 x.5），SCREEN_UV 是归一化屏幕 UV（0 到 1）。

## 3.7 一次顶点的完整旅程
读到这里你也许能机械地复述六层空间链，但仍对他们为什么要这样串起来没"画面感"。这一节给你一个统一的生活隐喻——把整套管线想象成一次"演员从化妆室到银幕"的旅程。

### 3.7.1 六层空间 = 六个房间

```
化妆室      →      舞台      →      摄影机视角      →      镜头框架      →      3D 底片      →      银幕
模型空间          世界空间           视图空间               裁剪空间             NDC            屏幕空间
```

- 
**化妆室（模型空间）**：演员自己看自己。化妆镜里的位置是"我的左手边 30 厘米"——相对于自身的坐标。导演喊"出门"，演员出门；这里的位置数字不会因为剧组搬到北京还是上海而改变。

- 
**舞台（世界空间）**：所有演员一起拍戏的共享场景。"我在舞台中央偏左两米"——这是世界坐标。化妆出来的演员从化妆室被 MODEL_MATRIX（化妆室的坐标）搬到舞台上。多组演员共享一个舞台，所以可以互相判断谁在谁的左边。

- 
**摄影机视角（视图空间）**：导演开始开机。摄影机一脚踩在原点，看着 -Z 方向。原本舞台上的演员被 VIEW_MATRIX 搬到"以摄影机为原点"的坐标系——"演员在我镜头前方 5 米"而不是"演员在舞台中央"。从此每个深度都是"距镜头多远"，投影计算与摄影机的世界位置脱钩。

- 
**镜头框架（裁剪空间）**：摄影师要决定"画面里收什么"。视锥体就是镜头框架：近平面是不挡镜头的最近距离、远平面是"再远就不拍了"的截断、FOV 是镜头角度。PROJECTION_MATRIX 做两件事——先把视锥体"挤"成一个长方体，挤压的同时把"这个顶点离镜头多远"记进 w' 当深度账本（w' = -z 视图空间）；再把长方体平移缩放成统一的标准坐标。挤压前 GPU 还要在等比线性空间里裁一下：框架外的演员直接剪掉（裁剪），用 -w' ≤ 坐标 ≤ w' 这种等价于"÷w 后是否在 [-1,1]³ 内"的判据做一次线性测试——GPU 不用先做除法就能决定扔掉谁。

- 
**3D 底片（NDC）**：留下的演员做透视除法 ÷w'——(x'/w', y'/w', z'/w') 之后都归一化到同一个 [-1, 1]³ 的三维标准底片里。"近大远小"在这里真正显形：远处演员 ÷ 大 w'、x'/y' 被"压"小，在底片上向中心收缩；近处演员 ÷ 小 w'、保留原比例，在底片上更靠边。这张底片是 3D 的。除了 x/y 平面位置，还保留了 z 维度（即深度值），用 [-1, 1]³ 整个立方体表示，让所有可见顶点无论远近都在同一套坐标系里，方便后续做遮挡判断和深度测试。

- 
**银幕（屏幕空间）**：底片被冲洗成像素。视口变换把 [-1, 1] 映射到 1920×1080 之类的真实分辨率，光栅化器把三角形铺成像素，每个像素拿到自己的 FRAGCOORD 和插值后的 UV，进入 fragment() 着色。

### 3.7.2 为什么链路这么长？一句话总结
每一层都在解决一件事：

| 空间 | 解决的问题 |
| 模型空间 | "物体自身不变量"（法线、UV、规则形变） |
| 世界空间 | "物体之间的相对关系"（光、风、群组站位） |
| 视图空间 | "物体相对摄像机的距离"（深度、Fresnel、视角相关效果） |
| 裁剪空间 | "GPU 高效裁剪的标准形状"（用 w 兼顾透视） |
| NDC | "投影后的归一化位置"（透视除法显形后） |
| 屏幕空间 | "实际像素"（fragment 工作的地方） |

如果你在 shader 里看到 VERTEX，它说的是"模型说了算"的坐标；看到 CAMERA_POSITION_WORLD，那是世界空间；看到 VIEW、NORMAL（fragment 阶段），那是视图空间；看到 SCREEN_UV、FRAGCOORD，那是屏幕空间。**理解变量在哪个空间里，比记公式重要**。

## 3.8 深度缓冲与非线性深度
这一节是为高级章节储备的必备概念。你可以初读时只了解结论，等读后续时再回来细看。

### 3.8.1 深度缓冲
在光栅化阶段，每个片元除了 x/y 坐标，还带着一个深度值（来自 NDC 的 z）。GPU 维护一块叫深度缓冲的显存，记录了屏幕上每个像素"目前离相机最近的那个表面的深度"。

每次一个新片元到达：GPU 比较它的深度值和缓冲里已有的值。新片元更近 → 画上去并更新缓冲；新片元更远 → 丢弃（被遮挡）。这就是 ch1 提到的"深度测试"的底层机制。

在 Godot 中，你通常不需要手动操作深度缓冲——引擎根据物体的空间位置和渲染顺序自动处理。但在自定义 spatial shader 中，render_mode depth_test_disabled 可以关闭深度测试（用于全息 / 半透明等特殊效果）。

### 3.8.2 深度缓冲存的值 = NDC 的 z
**关键事实**：深度缓冲里存的不是"真实距离"，而是**NDC 的 z 分量**——也就是 3.6.3 节讲的那个非线性值。

```
depth_buffer = NDC.z   // Forward+/Mobile: [0, 1]，近=0，远=1
```

- 近平面（z = -near 视图空间）→ NDC.z = 0 → 深度缓冲 = 0
- 远平面（z = -far 视图空间）→ NDC.z = 1 → 深度缓冲 = 1
- 中间值不线性，按 1/z 分布——近处精度高、远处精度低

### 3.8.3 混合模式：着色之后的另一道判决
深度测试是"非此即彼"——要么画上去、要么丢弃。但有时你需要"掺在一起"——这就是混合。

- **Alpha Blend**（透明度混合）：新颜色按 alpha 比例叠加到旧颜色上，final = new * alpha + old * (1 - alpha)
- **Additive Blend**（加法混合）：新颜色直接加到旧颜色上，final = old + new，只增亮不增暗——光晕、火焰、魔法特效
- 在 Godot 中通过 render_mode blend_mix、blend_add、blend_sub、blend_mul 控制
深度测试决定"要不要画"，混合模式决定"怎么掺到一起"。后面的章节（ch14 溶解、ch16 复古后处理）会频繁用到它们。

## 3.9 2D 是 3D 的特例
讲完 3D 六层链之后，再看 2D。**Godot 4 中 2D 渲染管线和 3D 是同一套**——2D 的所有矩阵都是 mat4，shader 也走相同的齐次坐标管线。2D 看起来简单，本质是 3D 管线在**正交投影**下的退化。

### 3.9.1 为什么 2D 也用 mat4？
设想你是引擎设计师。你有两条管线：

- 3D：6 层空间、mat4、齐次坐标、透视除法
- 2D：4 层空间、mat3（3×3 足够 2D 平移 + 旋转 + 缩放）、不需要 w
如果两套管线分开实现，GPU 端就要维护两套着色器编译器、两套内置变量、两套裁剪和投影路径。Godot 4 选择了**统一**：

- 2D 也用 mat4——3D 的 mat4 在 2D 中退化（第三行第三列恒为 (0, 0, 1, 0)，z 分量不变）
- 2D 也走齐次坐标 vec4(x, y, 0, 1)
- 2D 也走裁剪空间和 NDC——只不过因为 w 恒为 1，透视除法变成"除以 1"，无变化
- 2D 的"摄像机"用 Camera2D，但它在引擎内部被翻译成与 3D Camera3D 等价的"视图 + 投影"组合
代价是 2D shader 也得多写一些 4×4 矩阵；收益是引擎管线只需维护一套，2D 和 3D 共享同一份硬件加速。

### 3.9.2 2D 的五层链
把 3D 的视图空间和投影空间做"退化合并"后，2D 的空间链是五层：

```
局部空间 (Local)
    │  MODEL_MATRIX
    ▼
世界空间 (World)       —— 编辑器中的场景坐标
    │  CANVAS_MATRIX
    ▼
画布空间 (Canvas)      —— 屏幕左上角原点，范围 (0,0) → viewport_size
    │  SCREEN_MATRIX
    ▼
裁剪空间 (Clip)        —— [-1,1]（w 恒为 1，无透视）
    │  GPU 视口变换（自动）
    ▼
屏幕空间 (Screen)      → FRAGCOORD
```
注意 2D 多出"画布空间"这一层。原因是 Godot 把"摄像机变换"和"投影"分开了：

- **MODEL_MATRIX**：Local → World。和 3D 一样，物体自身的 transform 矩阵。
- **CANVAS_MATRIX**：World → Canvas。摄像机位置 / 缩放作用在这一步——Camera2D 移动时 CANVAS_MATRIX 跟着变。画布空间的原点是屏幕左上角，单位是像素，范围是 (0, 0) 到 (viewport_width, viewport_height)。
- **SCREEN_MATRIX**：Canvas → Clip。把像素坐标归一化到 [-1, 1]，相当于 3D 的 PROJECTION_MATRIX 在正交投影下的角色——只是更简单，纯线性缩放。
**2D 与 3D 的对应**：CANVAS_MATRIX 在 2D 里干的是 3D VIEW_MATRIX 的活儿——把世界搬到"以摄像机视角为原点"。SCREEN_MATRIX 干的是 3D PROJECTION_MATRIX 的活儿——投影到裁剪空间。区别是 2D 总是正交投影、w 恒为 1、没有透视除法变形。所以 2D会少一级，它把"裁剪"和"NDC"合并成一层，视口变换后直接到屏幕。3D 多出 NDC 一级是为了让 w 编码深度、÷w 显形近大远小。

### 3.9.3 2D 简化情形：世界 ≈ 画布
在普通 2D 场景没有 Camera2D（或相机居中、不偏移、不缩放）也没有 CanvasLayer 时，**世界空间和画布空间数值上等价**——只是原点平移。一旦引入移动的摄像机或多层 Canvas，两级明显分离：摄像机移动让画布坐标跟着平移、世界坐标纹丝不动。

本书多数 2D 案例是简化情形，初读时可把"画布"和"世界"暂时当成一回事，但要知道**它们在引擎里是两层独立的坐标**。

**注意**：当场景中使用 CanvasLayer 或 SubViewport 时，每个层有独立的世界和画布空间。只有同一层内的节点才共享坐标系。本书不涉及多层 Canvas。

## 3.10 3D 矩阵全系列速览
Godot spatial shader 在 vertex() 中暴露了以下矩阵变量。这里不逐一展开用法（后面实战章会调用），但要求你在需要时知道"哪个矩阵存在"：

| 矩阵名称 | 方向 | 从 → 到 | 典型用途 |
| MODEL_MATRIX | 正向 | Model → World | 把局部坐标推到世界坐标 |
| INV_MODEL_MATRIX | 反向 | World → Model | 把世界向量转回局部空间 |
| VIEW_MATRIX | 正向 | World → View | 把世界坐标推到摄像机坐标 |
| INV_VIEW_MATRIX | 反向 | View → World | Billboard、从深度重建世界坐标 |
| PROJECTION_MATRIX | 正向 | View → Clip | 透视 / 正交投影 |
| INV_PROJECTION_MATRIX | 反向 | Clip → View | 深度缓冲反投影 |
| MODELVIEW_MATRIX | 正向 | Model → View | VIEW_MATRIX * MODEL_MATRIX（快捷方式） |
| MODELVIEW_NORMAL_MATRIX | 正向 | Model normal → View | 法线变换的专用矩阵（不含平移） |
| MODEL_NORMAL_MATRIX | 正向 | Model normal → World | 把模型空间法线推到世界空间 |

**MODELVIEW_NORMAL_MATRIX / MODEL_NORMAL_MATRIX 为什么单独存在？** 法线是方向向量，不是位置。如果直接用 MODEL_MATRIX 去乘法线，非均匀缩放会把法线掰歪。GPU 给你 MODELVIEW_NORMAL_MATRIX（MODELVIEW_MATRIX 逆转置的 3×3 部分）和 MODEL_NORMAL_MATRIX，省去你手动处理。

## 3.11 可视化练习：坐标就是颜色
纸上谈兵总是干涩的。做一个即时的视觉实验——**把顶点坐标直接映射成颜色**，让你亲眼看到不同空间坐标的差异。

下面代码是核心抽离，你不必完全理解每个细节（ch4 才会正式写第一个 shader），只需聚焦在"颜色 = 坐标"这个映射上。

```
shader_type canvas_item;

uniform int visualize_space = 0;
uniform float scale_factor = 512.0;

varying vec4 color;

void vertex() {
    vec2 local_pos = VERTEX;

    vec2 display_coord;

    if (visualize_space == 0) {
        // 局部空间：坐标固定，颜色永远不变
        display_coord = local_pos;
    }
    else if (visualize_space == 1) {
        // 世界空间：移动节点 → 颜色变化
        vec4 world_vec = MODEL_MATRIX * vec4(local_pos, 0.0, 1.0);
        display_coord = world_vec.xy;
    }
    else if (visualize_space == 2) {
        // 画布空间：移动摄像机 → 颜色剧变（2D 的"视图空间"对应物）
        vec4 world_vec = MODEL_MATRIX * vec4(local_pos, 0.0, 1.0);
        vec4 canvas_vec = CANVAS_MATRIX * world_vec;
        display_coord = canvas_vec.xy;
    }

    // 把坐标值映射到 0-1 的颜色范围
    color = vec4(
        clamp(display_coord.x / scale_factor, 0.0, 1.0),
        clamp(display_coord.y / scale_factor, 0.0, 1.0),
        0.0, 1.0
    );
}

void fragment() {
    COLOR = color;
}
```
**技术说明**：这段代码并没有修改 VERTEX——物体的形状和位置完全不受影响，正常运行在场景中。它只是把顶点坐标数据"偷"出来变成颜色画在物体表面，这是将数学量可视化的常用技巧。

**实操**：在 Godot 中创建这个 shader，挂到 Sprite2D 上（用默认 logo 作为纹理），加一个 Camera2D，切换 visualize_space 的值（0/1/2），观察：

- visualize_space = 0（局部空间）：无论怎么拖动物体或摄像机，颜色纹丝不动。因为相对自身，顶点坐标永远相同。
- visualize_space = 1（世界空间）：拖动节点，颜色随世界坐标变化——越往右越红，越往上越绿。但移动摄像机无影响——世界坐标不关心摄像机位置。
- visualize_space = 2（画布空间）：移动摄像机时颜色变化——摄像机一移，顶点相对于摄像机画布的坐标就全变了。这是"世界空间 vs 视图空间"在 2D 中的直观对照。移动摄像机之后需要运行场景才会看到变化。

## 3.15 本章小结
所有坐标变换可以浓缩成一句话：**变换后的坐标 = 矩阵 × 变换前的坐标**。Godot 把每一步的矩阵放在内置变量里等你去用。

掌握本章不要求你记住每个矩阵的精确数值——没人记这个。你要建立的是**空间感**：

- 当代码里出现 VERTEX，你知道它说的是"模型说了算"的坐标。
- 当你想让物体朝屏幕中心移动，你知道要去世界或视图空间取坐标。
- 当法线贴图不对劲，你第一反应是检查法线在哪个空间（模型？视图？世界？）。
下一章，你将用本章的空间概念亲手写出第一个 shader。届时你见到的每个内置变量，都会落在本章"空间归属清单"的某个格子中。
