# lmeeting：让游戏项目会议产生有效进展

围绕本次需要的决定、学习或协调结果主持会议。共同原则是：**先对齐目标与客观约束，从意见中发现问题，核实原因，讨论解决方法，落实验证和行动**。

在有备选方案的决策会中，采用用户提出的核心方法：**客观初筛 → 主观意见提供线索 → 提取并验证客观原因 → 针对问题寻找办法 → 保留、调整、验证或排除 → 定案执行**。主观排除用于发现遗漏问题，不能替偏好包装客观理由；能在约束内解决的问题，不直接作为淘汰依据。

## 1. 先判断这次会议要完成什么

- **筹备**：提供精简会前材料、核心问题、议程和期望产出。
- **主持**：每次推进一个问题，吸收真实发言，再更新记录；不替未发言者编造意见。
- **整理记录**：区分决定、建议、分歧、待验证和行动，不能把沉默写成共识。
- **仅同步信息**：优先采用简短书面更新；只有需要即时澄清、协调或共同讨论时再组织会议。已经要求开会时，直接提供轻量安排，不额外阻挡。

先选主目的：探索方案、作出取舍、解除阻塞、验收结果或复盘改进。混合会议分段标明目的；讨论问题与评价解决办法分开，避免刚发现问题就争论某个人的方案。创意探索先产生备选，协调会可以直接落实依赖，复盘先还原事实，不强制每类会议都有候选淘汰。

## 2. 会前统一讨论对象与边界

先读适用项目规范和相关已定规则，只取影响本次决定的内容。已有信息直接使用；关键缺项集中询问，同时继续准备不依赖答案的部分。

会前卡只需明确：

- 本次问题：写成可回答的一句话；例如“这次 Demo 是否需要加入装备耐久”，不要只写“聊装备系统”。
- 本次成功条件、范围和不讨论的内容；明确产品阶段、目标玩家与希望产生的体验。
- 已定目标、硬约束、可协商条件及关键未知。按需列出平台、设备、镜头、技术能力、预算、工期、质量与内容规模。
- 共同材料：同一版本的可玩构建、录像、规则、数据或候选方案；标明版本、条件和来源，避免各自凭记忆讨论不同对象。
- 关键名词与程度词的共同锚点：为可能存在理解差异的词准备具体案例。视觉词使用同类视角的图片或实机片段，玩法词使用明确情境、规则流程或可玩案例；注明来源和版本。
- 推进人、必要的专业参与者、记录人；需要决定时明确实际有授权的决策人，小团队可兼任。涉及不同领域权限时分开记录，不擅自赋予某人全项目裁决权。

状态和背景尽量会前阅读，会中处理差异、取舍与阻塞。只请会影响决定、提供必要证据或承担关键依赖的人参与相关段落；其他人看结论即可。

## 3. 分清事实、约束、原因假设和感受

| 类型 | 处理方式 |
|---|---|
| 可检查事实 | 给出版本、条件、数据、记录或可复现例子；多人认同不等于事实已验证。 |
| 项目目标与约束 | 区分已批准的硬要求与可协商边界。设定是项目选择，不是普遍真理，但是否符合明确设定可以核对。 |
| 原因假设与预测 | 写明依据、未知及什么证据会改变判断。“可能超期”“因为反馈弱所以无聊”都需要检验。 |
| 偏好和体验感受 | 如实记录，追问触发情境与目标玩家；不把它包装成事实，也不因为主观就否定其设计价值。 |

玩家报告“无聊、挫败、看不懂”是有效的体验反馈；能确认的是该玩家在该条件下表达了这种感受，不能直接推出所有玩家如此或某机制必然失败。将体验目标落实为可观察行为、访谈反馈和试玩验证，避免只看单一数值或只听团队喜好。

## 4. 用具体锚点对齐名词和程度

“Q版”“写实”“低多边形”“硬核”“快节奏”等词容易让每个人联想到不同对象。涉及方案目标或筛选条件时，先对齐这个词在本次会议中的具体含义，再讨论方案是否符合。不要把字典定义或某个人的专业地位当作已经对齐。

按以下方式处理：

1. **先让每个人指出具体例子。** 视觉问题优先展示图片或实际游戏镜头；玩法问题还原为“玩家在什么情境做什么，系统如何响应”。先暴露理解差异，不急着争论谁的叫法正确。
2. **将模糊程度拆成可观察维度。** 例如“Q版到写实”可拆为头身比例、解剖夸张、轮廓概括、材质真实度、贴图细节、光照方式和动作夸张程度。同一个游戏在各维度上可能并不处于同一位置。
3. **用锚点描述目标区间。** 选择两至三个具体游戏或图片作为共同基准，说明“哪个维度参考哪一个、希望接近到什么程度”。可用“角色比例接近 A，材质与光照接近 B，避免 C 的高频细节”，不要只写“做成 A 那样”。
4. **确认参会者理解的是同一目标。** 请相关人员用自己的话复述，或在锚点图中指出目标位置与不能接受的边界。复述不一致时继续澄清，不能把投票结果当成认知已经对齐。
5. **把锚点写入决定和验收。** 记录游戏名、具体截图或片段、版本、场景、镜头及参考维度。参考游戏是沟通基准，不能自动扩大成对其全部风格或实现方式的采用。

同一游戏可能因角色、场景、皮肤、镜头和版本呈现不同风格；只写游戏名称仍可能产生歧义。图片必须能代表实际讨论条件，宣传图和近景立绘不能直接代替实机远景目标。

普通术语分歧也用同一原则处理：先还原具体例子，再写出本项目采用的含义。例如讨论“即时制”时，明确单位何时行动、时间是否暂停、玩家能否同时下令以及系统如何结算。

## 5. 用客观因素初筛，用主观意见补充问题

已知违反硬约束、在本次边界内又无可行调整的方案先排除，记录依据和影响范围。未知可行性列为待验证，不混入已确认可行项。不要为明显不合格项无限寻找补救方法。

当已有规则不能解释分歧或怀疑有遗漏时：

1. **先独立记录。** 每人写担忧、想排除的部分和原因；没有担忧可不填。主张方案的人和决策人尽量在其他人独立记录后再表态。
2. **先听全，再讨论。** 轮流提出一项并澄清含义；较大团队可采用个人、两人、四人、全体逐级交流。
3. **从意见定位问题。** 追问“哪个情境发生了什么、影响哪个目标、有什么依据”。区分现象与推测原因，允许最后仅剩偏好，不补造客观理由。
4. **核实客观原因。** 检查证据、反例及适用范围。同类问题可归并，但先不将其写成淘汰规则；复盘可能有多个共同原因，不强求唯一根因。
5. **找解决方法。** 比较调整规则、表现、内容规模、实现方式或协作流程的办法；说明代价、收益、依赖和对核心体验的影响。原因不明时先设计能区分原因的验证。
6. **根据结果取舍。** 有依据证明能在边界内解决的，保留或调整；方法尚未证实的，指定验证；无法解决、代价超界或破坏核心目标的，才据此排除。可复用的解决办法与筛选条件一致应用于同类选项。

例：“这个技能没意思”可以追问到“连续几回合总是选同一个目标”。原因可能是收益差距、敌人配置或信息提示；先用记录和试玩区分，再试改收益、遭遇或提示。不能直接删技能，也不能把其中一个推测写成根因。

候选状态使用**通过 / 排除 / 待验证**；“调整”是处置方式，调整未验证前仍是待验证。问题讨论的最短记录为：**原始意见 → 问题与证据 → 原因假设 → 办法及代价 → 验证 → 结论**。

## 6. 按分歧类型选择主持方法

| 当前卡点 | 主持动作 | 得到什么就结束这一段 |
|---|---|---|
| 有人先表态，其他人跟随 | 先各自写，再同时展示或轮流说；有权决策者晚些表达偏好 | 独立意见和关键差异 |
| 各说各话 | 回到同一版本、具体例子和成功条件；用一句话复述对方问题供确认 | 共同的问题定义 |
| 使用同一个词却指向不同程度 | 展示具体锚点，拆分维度，让相关人员指出目标位置并复述 | 有来源、维度和边界的共同定义 |
| 事实或原因争议 | 写竞争解释，找已有证据；不足就安排最小验证 | 证据结论或验证任务 |
| 目标优先级冲突 | 展示各选项牺牲什么，由有授权者按项目目标取舍 | 明确优先级与承担的代价 |
| 已有方案，但没人提风险 | 问“如果本次目标失败，最可能在哪一步？”区分假想风险与已发生事实 | 少量关键风险、预防措施及检查人 |
| 老问题循环争论 | 回读已定结论与依据，检查是否有新证据或约束变化 | 保持决定，或仅重开受影响部分 |
| 话题跑远、全体陪少数人排查 | 标明是否阻碍本次目标；不阻碍的列入另议，专业排查只留相关人员 | 当前议题恢复推进，另议有承接人 |
| 临近结束仍无结论 | 把未决点拆成缺信息、缺权限、未达成取舍，安排对应下一步 | 如实记录未决定及解决条件 |

投票用于显示偏好或讨论优先级，不证明技术事实、不抵消硬约束，也不自动替代团队约定的决策权。需要共识时可问“有哪些仍会阻碍执行的实质异议”，不要把所有人同样喜欢方案作为默认完成条件。

讨论时间按任务调整。主持人可以提醒限时，到时选择作决定、指定验证、缩小范围或转另议；不要用时间到了强行制造通过。

## 7. 从可行方案中选择，并设计最小验证

客观筛选结束后，正向比较目标体验、预期价值、实现及维护成本、依赖和风险，避免只选“毛病最少”的方案。只使用影响本次决定的维度；评分说明依据，未经商定不制造精确权重。创意价值和体验判断可以保留为待验证的设计主张。

对影响大且证据不足的判断，优先安排原型、技术试验或针对性试玩。验证任务写清：

- 要回答的问题、关键假设，以及什么结果会支持或反驳它。
- 使用的版本、设备、对象与情境；基准方案或比较条件。
- 交付物、投入上限、负责人、检查时间、判定人。
- 成功、失败或证据不足时分别如何推进。

尽量控制能影响判断的条件；探索阶段可以组合试改，但要记录组合内容，不能据此单独归因。单个样本、小样本和专家判断可以支持下一步试验，不能冒充已验证的普遍结论。不要求所有小决定都制作原型。

可逆且影响小的决定可在已有权限内试行；影响广、修改成本高的决定需要相称证据，并遵守项目授权边界。提出暂行方案不等于获得执行许可。

## 8. 结束时落实决定、责任与验收

按会议目的输出**已决定 / 有条件决定 / 未决定**，或明确的学习结论、协调结果与下一步。只有真实批准才能写成已决定；已有批准不重复索取，AI 建议不等于团队拍板。

行动项至少包含：**一个牵头负责人、交付物、截止时间、依赖、验收人和完成条件**。必要时列协作者；“大家跟进”“继续优化”“加强沟通”不算可执行任务。缺人名、日期或预算就标待指定，不能虚构承诺。

排期包含整合、评审、测试和必要返工；区分工作量估计与完成日期。任务负责人不能独自控制的前置依赖，写明提供方和需要时间。

会末回读：“决定了什么，为什么，谁做什么，什么时候交，怎样算通过，什么情况重开？”记录主要异议、选择代价与验证条件，避免逐句抄录全部发言。下次相关会议先检查未完成行动和验证结果，不自动重讲所有背景。

默认交付精简记录；按需要使用模板中的部分表格。创建外部任务、通知人员、修改正式项目文档、发布或部署仍按本次实际授权执行，技能不提供额外权限。
